一句话结论：推荐系统上线后，模型本身只决定效果上限，特征口径、延迟预算、降级策略、实验分流决定你能拿到多少。绝大多数「上线没效果」，问题都不在模型结构上。

这一页会反复出现的三个词，先解释掉：

P99：把 100 次请求的耗时从快到慢排队，第 99 个的耗时。它比"平均耗时"更能反映用户体感——平均 30ms 但 P99 是 500ms，意味着每秒都有人在等半秒。

QPS：每秒请求数（Queries Per Second），用来衡量并发压力；峰值 QPS 决定你要部署多少台机器。

降级：某一步超时或报错时，退回一个更便宜但还能用的方案（比如精排超时就按粗排分数出结果），保证页面先出来，而不是白屏。

ARCHITECTURE在线架构全景：一次请求的 100ms

线上推荐不是一个模型，而是「一条串行主链路 + 三个旁路」。主链路决定延迟，旁路决定效果上限。

先记住候选集的数量级变化，后面所有设计都围绕它：百万级物料库 → 召回取 2000 → 过滤剩 800 → 粗排 150 → 精排 50 → 重排出 10 条。 每一步都在做同一件事：用越来越贵的模型，算越来越少的候选。粗排之所以存在，就是因为精排太贵，不能对 800 个候选都跑 DIN。

实线是同步主链路（计入 100ms 预算）；虚线是旁路或异步链路（不计入首屏延迟，但决定模型能学到什么）。

延迟预算怎么分：100ms 是设计出来的，不是测出来的

总预算 P99 100ms，分配如下。注意两点：

1）每层超时要比预算再留 20% 余量。比如精排预算 40ms，实际设 48ms 超时；因为一旦超时你要有几毫秒去做降级决策和组装，而不是卡在超时点上。

2）各阶段 P99 不能简单相加。数学上独立随机变量的 P99 之和会大于整体的 P99；但线上各阶段共享 CPU、共享下游、共享 GC 停顿，尾部是相关的，实测往往接近相加。所以工程上按「最坏情况相加 = 100ms」倒推，是更安全的做法。

超时(层) = 预算(层) × 1.2   |   剩余时间 = deadline − now deadline 是"这次请求最晚必须在哪个时刻返回"的绝对时间，now 是当前时刻，两者相减就是还能花的时间。下游必须用「剩余时间」而不是自己的固定超时：网关传下来的 deadline 是绝对的，剩 18ms 时召回的 20ms 超时就该截断成 18ms。 
# 请求上下文里携带绝对 deadline，逐层传递
ctx = {
  "trace_id": "r-8f3c...",
  "deadline_ms": 100,        # 从网关收到请求开始计时
  "uid": 10086,
  "stage_budget": {"recall": 20, "prerank": 15, "rank": 40, "rerank": 5}
}

def call_stage(name, fn):
    remain = ctx["deadline_ms"] - elapsed()
    if remain <= 0:
        return fallback(name)              # 直接降级，不再发请求
    timeout = min(ctx["stage_budget"][name], remain)   # 关键：取小值
    try:
        return fn(timeout_ms=timeout)
    except Timeout:
        metrics.inc(f"{name}_timeout")
        return fallback(name)

超时与降级：每一层都要想好「算不出来怎么办」

降级不是异常处理，是产品设计。你要提前决定：相关性掉多少是可以接受的？白屏是绝对不能接受的，所以任何一层挂掉都必须有兜底。

全链路超时剩余 < 10ms返回该用户上一次的结果快照（缓存 5 分钟）内容重复刷新后内容不变

新手最常犯的错：给每一层都设 100ms 超时。结果是一次请求最坏要 400ms，网关早就断了，用户看到白屏。正确做法是总 deadline 100ms，逐层扣减；下游拿到的永远是「剩余时间」。

真实取舍：晚高峰 19:30，精排 GPU 队列积压，P99 从 45ms 涨到 180ms。止损动作是把精排候选从 150 砍到 80、batch 从 32 降到 16，同时把超时阈值卡在 40ms，超出直接退回粗排。结果是 CTR -1.2%，但接口成功率从 97.4% 回到 99.93%。

这个决策的对错标准不是「CTR 掉了」，而是「掉 1.2% CTR 换 2.5 个点成功率」值不值。在信息流产品里通常值——白屏一次，用户当天可能就不来了。

FEATURE特征服务：线上线下为什么总是不一致

离线是一个可以看全量、可以回刷、可以重算的世界；在线是一条一条查、必须在 10ms 内返回、只能看「现在」的世界。这两个世界的缝隙，就是绝大多数线上事故的入口。

离线特征 vs 在线特征：不是同一份东西

保证一致的四个抓手

1. 一份定义（Feature Registry）

特征名、类型、默认值、时间窗口、数据源、负责人，全部写在一处。离线任务和在线服务从同一个 registry 生成代码，禁止两边各写一份 SQL。

2. 一份转换逻辑

归一化、分桶、log 变换这些预处理，必须固化进模型（作为模型的一部分导出），或训练与服务共用同一份 Python 函数。最怕「训练时做了标准化，线上忘了」。

3. 日志即样本

在线打分时把实际用到的特征向量写进曝光日志，训练直接用这份日志。这是最彻底的方案——天然一致，代价是存储翻几倍，且无法回刷历史。

4. 持续对账

每天抽样 1 万个请求，把线上特征落盘，与离线重算结果逐字段比对：缺失率、均值差、KS、PSI。差异超阈值就报警，不等指标跌了才发现。

工程上的优先级：日志即样本 > 统一 registry > 每日对账 > 靠人 review。前两个能消灭 80% 的不一致，后两个只能让你早一点发现。如果团队只做一件事，做「把 serving 的特征落进日志」。

特征穿越的三种典型形态

特征穿越（feature leakage）的本质是：训练时你知道了预测时刻不可能知道的信息。它在离线表现为「AUC 高得离谱」，上线表现为「效果归零」。三种形态要能脱口而出：

形态典型特征错在哪识别信号
① 用未来统计item_ctr_7d、user_cnt_30d、item_gmv_1d统计窗口覆盖了样本发生之后的时间，把未来的点击算进了过去的特征单特征 AUC 高到 0.75+；按天切开后，越靠后的日期特征越强
② 用 label 派生is_clicked_before、video_finish_rate、order_amount、退款率这些值只有「点击/下单之后」才产生，等于把答案喂给模型某特征在正样本上 100% 有值、负样本全缺失
③ 时间口径不一致所有带窗口的聚合离线按自然日 dt、在线按滑动窗口；离线用 UTC、线上用本地时区；离线含当天、线上到昨天离线分布与线上分布 PSI > 0.25；误差集中在跨零点时段

一个反直觉的判据：如果某个特征的加入让 AUC 从 0.80 跳到 0.92，先别高兴，先查穿越。真实的业务信号很少能一次贡献 10 个点。经验上，单特征 AUC 超过 0.7 就要逐条审计它的时间线。

具体例子：item_ctr_7d 到底该用哪段时间

这个特征在几乎所有推荐系统里都存在，也是穿越率最高的一个。假设样本是 6 月 3 日 的一条曝光，用户在这个时刻看到了物品 A：

写法统计窗口是否穿越说明
❌ 全量快照整张表的 6/1–6/7严重穿越用到了 6/4–6/7 的点击，其中包含这条样本自己的结果
❌ 当天含当日5/28–6/3 整天穿越6/3 的点击发生在曝光之后，样本时刻还看不到
⚠️ 差一天5/27–6/2勉强可用保守但安全；牺牲了最新一天的信息
✅ 正确（离线）[6/3 00:00 − 7d, 6/3 00:00)，且只取 event_time < 样本 event_time不穿越as-of join，按样本自己的时间戳取窗口
✅ 正确（在线）请求时刻 T 往前推 7 天，截止到 T−1 天不穿越因为离线聚合有 1 天延迟，线上必须留同样的延迟才能对齐
 
-- 正确做法：as-of join，按样本时间取「当时可得的」统计
-- 关键点 1：窗口右端是样本时间，不是今天
-- 关键点 2：再往前留 1 天，覆盖日志延迟
WITH stat AS (
  SELECT item_id, dt,
         SUM(clicks)   AS clicks,
         SUM(impressions) AS imps
  FROM dwd_item_hourly          -- 每小时聚合，T+1 可用
  WHERE dt BETWEEN date_sub('${sample_date}', 8)
               AND date_sub('${sample_date}', 1)
  GROUP BY item_id, dt
)
SELECT s.label,
       COALESCE(SUM(st.clicks) / SUM(st.imps), 0.0) AS item_ctr_7d,
       SUM(st.imps) AS item_imp_7d          -- 顺便带上置信度：曝光太少不可信
FROM samples s
LEFT JOIN stat st
  ON st.item_id = s.item_id
 AND st.dt >= date_sub(s.dt, 7)
 AND st.dt <  s.dt                        -- 严格小于样本当天
GROUP BY s.request_id, s.label

真实数字：一个短视频项目里，item_ctr_7d 最初用全量快照，离线 AUC 0.856；改成 as-of join 后掉到 0.831。掉的这 2.5 个点全是虚高——线上本来就不可能拿到未来数据。

更有意思的是：修正后线上 CTR 反而 +1.8%。因为旧特征在线上大面积缺失（新物品没有 7 天统计），模型学到的其实是「有没有统计值」这个代理信号，而不是真实点击率。带上 item_imp_7d 做置信度后，冷启动物品的排序明显改善。

版本管理、回填与监控

特征不是一个字段，是一个有版本的资产。改口径必须像改接口一样：新版本、双写、灰度、可回滚。

定义 v2registry 里新增 item_ctr_7d@v2，不覆盖 v1
双写离线与在线同时产 v1 / v2，跑 3~7 天
对账抽样比对分布：均值、分位数、PSI、缺失率
回填重跑历史，写新分区，不动老分区
切换训练用 v2 → 灰度 5% → 全量，保留 v1 热备

回填（backfill）有三个坑：耗时（30 天历史 × 10 亿行，Spark 要跑几小时）、口径漂移（回填用的是今天的数据源，而历史时刻的数据源可能已经变了）、覆盖写（新分区写错路径，把线上正在读的分区覆盖了）。所以回填必须写独立路径，验证后再切。

DEPLOY模型上线：从 checkpoint 到线上 5% 流量

训练出 AUC 0.858 只是拿到了一张门票。真正的卡点是：导出后的模型，能不能在线上用同样的特征、同样的预处理，打出同样的分数。

① 训练固定数据快照、随机种子、特征版本
② 导出图 + 权重 + 预处理，一起打包
③ 一致性校验同批请求，双端打分，误差 < 1e-4
④ 注册不可变 model_id，写元数据
⑤ 灰度影子 → 5% → 20% → 50% → 100%
⑥ 观测 / 回滚指标 + 延迟 + 错误率，30s 可回

导出：最容易丢东西的一步

导出不是 torch.save(model) 就完事。一个能上线的模型包必须包含四样东西：计算图（结构）、权重、预处理（归一化参数、词表、分桶边界）、输入输出契约（字段名、类型、shape、默认值）。少任何一样，线上就会用错。

不要导出整个 Python 对象（pickle）。它依赖训练时的类定义和库版本，线上环境稍有不同就加载失败，而且有反序列化安全风险。用 SavedModel / ONNX / TorchScript 这类与代码解耦的格式。

# 训练 → 导出 → 一致性校验 → 注册（伪代码）
def train_and_deploy(cfg):
    ds = load_snapshot(cfg.data_version)          # 数据快照必须固定，能复现
    model = build_model(cfg)
    model.fit(ds.train, ds.valid)

    # 1) 导出：图 + 权重 + 预处理参数
    export_dir = f"dist/{cfg.model_name}/{cfg.model_id}"
    export_saved_model(
        model,
        export_dir,
        preprocess=ds.transform.params,           # 标准化均值/方差、词表、分桶
        signature={"uid": "int64", "item_ids": "int64[200]", "features": "float32[200,64]"}
    )

    # 2) 一致性校验：拿 1000 条线上真实请求，双端打分
    batch = sample_online_requests(n=1000, date="yesterday")
    y_train_side = model.predict(batch)            # 训练框架
    y_serve_side = client.predict(export_dir, batch)  # 线上 serving
    diff = abs(y_train_side - y_serve_side).max()
    assert diff < 1e-4, f"serving skew: {diff}"    # 超了就别发布
    assert abs(auc(y_serve_side, batch.y) - auc(y_train_side, batch.y)) < 0.002

    # 3) 注册：model_id 不可变，写清血缘
    registry.register(
        model_id=cfg.model_id,                     # 例：20240603-1430-a3f2
        path=export_dir,
        data_version=cfg.data_version,
        feature_version=cfg.feature_version,

    )

版本、灰度、回滚

版本不可变

model_id 一旦发布就不能改内容，例如 20240603-1430-a3f2。永远不要用 latest 这种会漂移的标签指向线上——三个月后没人知道线上跑的是哪个模型。

影子流量先行

新模型接 100% 线上请求但不影响结果，只记录分数。对比新旧分数的均值、分位数、排序一致性（Top10 重合率）。差异大就说明有 skew，别放量。

双版本常驻

新旧模型同时加载在显存里，切换只是改路由权重。这样回滚是秒级；如果需要重新下载 2GB 模型，回滚要 5 分钟，指标早跌穿了。

EXPERIMENT实验平台：让「涨了 1%」这句话可信

实验平台的价值不是开开关，而是让结论可归因、可复现、经得住追问。一次分流写错，后面所有分析都是白算。

分流：用户级 hash 是底线

bucket = murmur3(uid + "_" + salt) % 10000 同一用户在实验期内永远落在同一个桶；salt 决定「这次实验怎么切」，换 salt 就是换一组人。

三个必须遵守的规则：

1）按用户分，不按请求分。如果每次请求随机，用户会一会儿看到新模型一会儿看到旧模型，体验抖动，而且点击行为被两种策略混合污染，谁也说不清效果来自哪个。

2）不要用设备号、手机号尾号、注册时间取模。这些字段本身与人群相关：手机尾号 0–4 和 5–9 的用户，在新老程度上可能有系统性差异，一上来就分流不均。

3）分层（layer）+ 互斥（mutex）。不同模块用不同 salt 分层，层与层之间正交，所以召回实验和 UI 实验可以同时跑；同一层内的多个实验必须互斥，否则一个用户同时进两个实验，效果无法拆开。

概念怎么做解决什么问题踩坑点
用户级 hashmurmur3(uid + salt) % 10000同一用户策略稳定，指标可比hash 函数要固定，不能中途换实现
分层实验UI 层 / 召回层 / 排序层 / 广告层各用独立 salt多实验并行，互不干扰层之间如果共享资源（同一 GPU），仍会互相影响延迟
互斥实验同层内实验组桶位不重叠，或加互斥组 ID避免同层两个策略叠加互斥组会把流量切碎，样本量要重新算
流量比例1 万桶，实验 500 桶 = 5%小流量试错5% 流量下，检测 1% 提升要跑很久
 
import mmh3

def bucket(uid: int, salt: str, total: int = 10000) -> int:
    # 用无符号 32 位，避免负数取模在不同语言里不一致
    return mmh3.hash(f"{uid}_{salt}", signed=False) % total

# 实验配置：一个实验 = 一层 + 一组互斥桶位
exp = {
    "name": "rank_din_v3",
    "layer": "ranking",            # 与 recall / ui 层正交
    "salt": "ranking_2024q2",      # 换实验换 salt
    "buckets": {"control": [0, 499], "treatment": [500, 999]},  # 各 5%
    "unit": "uid",
    "primary_metric": "ctr",
    "guardrail": ["p99_latency", "unfollow_rate"]
}

def assign(uid: int) -> str:
    b = bucket(uid, exp["salt"])
    for group, (lo, hi) in exp["buckets"].items():
        if lo <= b <= hi:
            return group
    return "outside"               # 90% 流量不参与，保持线上原策略

A/B 的样本量直觉：1% 的提升很贵

两个比例的显著性检验，样本量近似公式（α=0.05，power=0.8）：

n ≈ 16 × p(1−p) / δ²   （每组样本量，p 为基准值，δ 为绝对提升） 16 是 α=0.05、power=0.8 对应的常数，够用了；严格的实验平台会用 15.7 或精确公式，差别不大。

基准 CTR 5% 时，不同提升幅度需要的样本量：

相对提升CTR 变化δ（绝对值）每组所需曝光2000 万/天、50/50 下的理论时长
+0.5%5.00% → 5.025%0.00025≈ 1216 万约 1.2 天
+1%5.00% → 5.05%0.0005≈ 304 万约 7~8 小时

理论时长 ≠ 实验时长。上表只回答「统计上够不够」，不回答「结论对不对」。你还需要覆盖完整的一周（工作日 vs 周末行为差异）、跨过 novelty effect（新模型前几天的虚高）、避开大促和节假日。所以一次正经的排序实验，至少跑 7 天，重要决策跑 14 天。

关于「显著」的三个常见误解：

① p < 0.05 不代表「A 有 95% 概率更好」。它的意思是：如果 A、B 真的没差别，出现这么极端结果的概率小于 5%。你应该看的是置信区间——「CTR +1.8%，95% CI [+0.4%, +3.2%]」比「p=0.03」有用得多。

② 同时看 10 个指标，至少一个「显著」的概率约 40%。所以实验前必须指定一个主指标，其他作为护栏指标（不能变差），不要在结果出来之后挑一个涨得最好看的讲。

③ AA 测试的假阳性率就是 5%。跑 20 次 AA，平均有 1 次会「显著」。这不是平台坏了，是统计规律。上线前跑 AA 的目的是验证分流和指标计算正确，不是保证永远不显著。

离线指标与线上指标：AUC 到 CTR 不是线性

AUC 衡量的是全局排序能力；线上只消费排序结果的前 10 个位置。这意味着：模型在长尾物品上排得更准，AUC 会涨，但用户根本看不到那些物品，CTR 可能一动不动。

离线指标线上指标正常情况下什么时候会背离
AUC / LogLossCTR同向，但幅度不成比例AUC 提升集中在中后段；或分数校准变差
Recall@100人均时长召回率涨 → 候选池更全召回进来的都是「相关但不好看」的内容
NDCG点击深度同向位置偏差让离线 NDCG 虚高
校准误差 ECE广告收入 / eCPM校准好 → 出价合理校准差时 CTR 可能没变，但收入跌
多样性指标次日留存多样性高 → 长期留存好短期 CTR 反而下降（用户点得少但看得久）

两个真实方向相反的例子：

① DIN 相比 DeepFM，离线 AUC +1.1pt（0.847 → 0.858），线上 CTR +1.8%。方向一致，因为收益集中在头部候选的排序精度上。

② 某次加了一个强序列特征，离线 AUC +0.8pt，线上 CTR −0.5%。查下来是分数分布变得更极端：模型把「用户刚看过同类」的内容推到极致，导致首屏同质化，用户刷两次就走了。AUC 涨的是「猜得准」，跌的是「看得爽」。

一个「实验结论不可信」的案例

某次排序模型实验，跑了 3 天，实验组 CTR −4.2%，看起来是模型变差了，团队准备放弃。复盘时发现三个问题叠加：

问题具体表现怎么发现正确做法
分流不均用「手机号尾号 % 100」分桶，实验组新用户占比 32%，对照组 21%。新用户 CTR 天然低，整体被拉低做 SRM 检验（分流比例卡方），并检查实验组/对照组的人群结构改用 murmur3(uid + salt)，分桶后立即做 AA
指标被污染同期另一个团队改了曝光埋点，实验组先上线，日志多了 7% 的重复曝光，分母虚高对数仓日志量与客户端上报量，发现比值异常实验期冻结埋点变更；主指标用「去重后的曝光」
实验期太短周五上线，只跑了 2 天，正好覆盖周末（时长天然高），周一回落后看起来暴跌按天画指标曲线，看到明显的周期性至少跑满 7 天，且以「周同比」而不是「实验期均值」判断

修正分流、重跑 7 天后，结论反转：CTR +1.3%。如果当时直接下结论「模型不行」，就白白丢了一个正收益的版本。实验的第一原则：先证明实验本身是干净的，再谈效果。

SRM（Sample Ratio Mismatch）是实验的第一道体检。设计 50/50，实际 50.4/49.6 可以接受；如果卡方检验 p < 0.001，说明分流、埋点或数据链路有 bug，此时所有指标结论直接作废，不要解释、不要调参，先修分流。

四个高频问题的具体打法

① 冷启动：按行为量分三段，别用一套策略

新物品同理，但方向相反：新用户缺的是「用户信号」，新物品缺的是「物品信号」。所以一个靠人群先验，一个靠内容理解（标题 / 封面 / 类目向量）。

② 位置偏差：训练时用位置，推理时把位置抹掉

P(click | user, item, pos) ≈ σ( f(user, item) + b(pos) ) 把「相关性」和「位置」拆成两项：f 学用户物品匹配，b 学位置带来的额外点击。推理时只保留 f，等价于把 pos 置 0（PAL，Position-Aware Learning）。

实现上有两种做法：（a）训练时把位置当特征，推理时统一填 0，简单但要保证位置特征没有和 item 特征交叉；（b）单独一个 bias tower 只吃位置，主塔完全不看位置，更干净，工程上多一个输出头。无论哪种，都要用位置随机化的小流量实验来验证去偏是否真的有效。

③ 反馈闭环：用 IPS 给「没被推过的」内容一个公平的评估

IPS(π_new) = (1/n) Σ [ π_new(aᵢ | xᵢ) / π_old(aᵢ | xᵢ) ] · rᵢ π_old 是产生日志的旧策略，π_new 是待评估的新策略。只有旧策略以非零概率选过的动作才能被估计——所以必须保留随机探索流量，否则分母为 0。

直觉：旧策略很少推的内容，一旦被推了，它的反馈要放大（因为样本稀有）；旧策略天天推的内容，权重要压低。这样评估出来的新策略效果，才不会被旧策略的偏好带偏。方差很大，实践中用 clipping（把权重截到 10 以内）或 DR（doubly robust）降方差。

④ 延迟抖动：先分层看 trace，再怀疑模型

  • 看是全局还是单实例：单实例 → 机器 / 热点；全局 → 下游或流量
  • 看 trace 里哪一段涨：召回 / 特征 / 模型 / 组装，各段分别看 P99
  • 看依赖：Redis 大 key、MySQL 慢查询、下游超时重试放大
  • 看运行时：CPU 打满、GC 停顿、连接池耗尽、线程数打满
  • 看流量结构：是否有大促、爬虫、热点事件导致某类请求暴增
  • 最后才看模型：batch 是否堆积、是否有超大 item 列表请求

排查的通用原则：从外到内，从便宜到贵。先确认「数据对不对」，再确认「特征对不对」，再确认「模型对不对」，最后才怀疑「策略设计」。顺序反了，你会花两天调模型，最后发现是埋点重复上报。

广告是推荐系统里唯一「每一次曝光都直接对应钱」的场景，所以它的工程约束比内容推荐更硬：算错一次出价，就是真金白银。

一个预算超投的例子：某广告主日预算 5 万，晚上 21 点已经消耗 5.8 万。原因不是计费错，而是pacing 用的消耗数据延迟 15 分钟，而晚高峰 QPS 是白天的 3 倍——15 分钟足够多花掉 8000 元。修复方式是把消耗计数改成准实时（流式聚合，延迟 < 1 分钟），并在预算消耗到 90% 时把曝光概率线性压到 0。

广告系统的容错原则：任何依赖 T+1 数据的控制回路，都不能用来做分钟级的预算决策。

作弊识别不要只看 CTR。真实的作弊流量往往是「点击多、停留短、无转化、设备集中」。比较有效的组合特征：点击间隔方差极小、同一 IP 下设备数异常、点击后 1 秒内退出、从无深页行为。单看 CTR 高，会把「素材特别好」的广告也误杀。

政务 / 行业场景：合规、可解释、公平性（简述）

这类场景的第一性原则和互联网相反：不是「效果最大化」，而是「不出错、说得清、可审计」。三个硬约束：

合规

数据最小化：只收集与政策匹配直接相关的字段；敏感字段（身份证、健康状况）不进入模型，只做规则判断；全链路留痕，能回答「这条推荐依据什么」。

可解释

输出必须带理由：命中哪条政策条件、匹配了哪些关键词、企业哪项资质符合。模型只做排序，不做「是否推荐」的最终决定——规则优先，模型兜底。

公平性

按企业规模 / 地域 / 行业分组评估曝光率与通过率，差距超过 5 个百分点要解释。不能因为「小微企业历史数据少」就系统性少推。

这块的完整做法（规则引擎、语义召回、漏推 / 误推评估、公平性指标）在项目二里展开，这里只要求你能说出「为什么政务不能纯用大模型」：不可解释、不可审计、会编造，而且漏推的代价远大于误推。

RECAP一页速记：上线前该背下来的六句话

工程部分最怕"都知道一点、串不起来"。合上页面前，用这六句把整章串一遍。

  1. 100ms 是设计出来的，不是测出来的：召回 20–30ms、粗排约 10ms、精排约 35ms、重排约 5ms，剩下的给网络与序列化。每一层都必须有超时和降级——没有降级方案的链路等于没有 SLA。
  2. 特征一致性靠四个抓手：一份代码（离线在线同源）、同一时间语义（event_time 而不是处理时间）、版本号 + 可回填、监控缺失率与分布漂移。少一个，早晚出事故。
  3. 上线五步：导出并校验（特征顺序、归一化参数、embedding 表）→ shadow 比对 → 1% → 5%~10% → 全量；回滚目标 30 秒，靠模型热切换 + 配置开关，不靠重新发版。

  5. 排查顺序永远是"先便宜后贵"：看日志 → 看分群 → 看单特征 → 做实验 → 最后才怀疑模型。一上来就说"模型不行"，通常会被数据打脸。

为什么离线 AUC 提升 1% 线上可能完全没变化？

因为两个指标衡量的不是同一件事。AUC 看的是全库、全候选的排序质量，而线上只消费前 10 个位置。如果提升主要来自中后段（比如长尾物品排得更准了），用户根本感知不到。

另外三种常见原因：① 离线评估带了位置偏差，AUC 涨的是「位置 → 点击」而非相关性；② 离线样本只来自曝光空间，和服务空间不一致；③ AUC 涨了但校准变差，精排分数被下游按 eCPM 混排时反而不占优。

所以正确做法是：离线看 AUC + 校准 + 分位置 NDCG，上线前做 shadow，最后只认线上 A/B。

特征穿越怎么发现？给我一套可执行的检查顺序。

第一步，看单特征 AUC。任何一个特征单独用就能到 0.75 以上，立刻怀疑。真实业务里除了「强 ID 类」特征，很少有这么强的信号。

第二步，审计时间线。把这个特征的窗口右端写出来：是「样本时刻」还是「今天」？如果是后者，基本可以判定穿越。再检查是否用了点击后才产生的字段（完播率、转化金额、退款率）。

第三步，做「去掉该特征重训」的消融。AUC 掉 3 个点以上、且线上效果不变，说明这个特征在线上本来就没有可用值，离线涨的全是假的。

第四步，按天切开验证。穿越特征在越靠近「数据截止日」的样本上越强，AUC 会随时间出现异常上升的斜率。

某一路召回超时了怎么办？为什么不干脆给全链路 200ms 算了？

多路召回是并行的，单路超时（超过 20ms）直接丢弃该路结果，用剩下几路继续，召回候选从 2000 降到 1300 左右，召回率损失 3~5 个点，用户基本无感。如果全部失败，落到 Redis 里的「热门 + 同城」兜底列表。

不能给 200ms 的原因是产品约束：首屏超过 100ms 用户能明显感到卡顿，超过 200ms 会开始退出。而且延迟预算是逐层扣减的——你给召回 200ms，精排就没时间了。真正该做的是把总 deadline 传下去，每层用「剩余时间」做超时。

新物品完全没有曝光，怎么评估它的召回 / 排序效果？

没有曝光就没有 label，不能用 CTR 评估，只能用代理信号 + 受控实验：

① 内容侧评估：用标题 / 封面 / 类目向量算「与用户历史兴趣的语义相似度」，看它是否能进入召回池（Recall@K 的内容代理版）。② 保量曝光：每天强制给新物品 500 次曝光，用这批随机流量算无偏 CTR，再和同品类老物品比。③ 看长期指标：30 日存活率、新物品进入 Top10 的比例、作者覆盖率。

关键是不能用「当前策略产生的日志」评估新物品——它没被推过，日志里根本没有它，这就是反馈闭环下的样本偏差。

A/B 跑了两天，p=0.02，能直接上线吗？

不能。先过三道关：

① SRM：实际分流比例是否符合设计（卡方 p > 0.001）。不均则结论作废。② 周期：两天没有覆盖完整周，工作日和周末的行为差异很大；同时要警惕 novelty effect——新策略前几天通常虚高，第 7 天回落后可能归零。③ 指标：主指标是否实验前就指定？护栏指标（延迟、负反馈、退订）有没有变差？

实操标准：至少跑满 7 天，看置信区间而不是只看 p 值，主指标正向且护栏指标不劣化，才放量。

线上 CTR 突然跌了 5%，说一下你的排查顺序。

按 数据 → 特征 → 模型 → 策略 → 外部 走，从便宜到贵：

数据：日志量、去重后的曝光数、分区产出、埋点版本。分母变了最常见，五分钟能排除。特征：缺失率、PSI、特征版本、新鲜度；对照训练期分布。模型：今天有没有发版？有就先回滚；再看分数分布和 ECE；确认线上 model_id 是不是你以为的那个。策略：规则、重排、频控、缓存 key、实验重叠。外部：节假日、竞品、舆情、客户端改版。

同时看 P99 和降级次数：如果精排超时率涨了，CTR 跌就是降级的副产品，不是模型问题。
