先把两个词钉死，后面就不会绕。

召回（retrieval）：从几百万候选里，用便宜的方法快速捞出几百到几千个"可能相关"的，目标是别漏，不追求排得准。

排序（ranking）：对这几百个候选，用贵的方法精确打分，目标是排得准，因为用户只看前几个。

一句话：召回决定天花板，排序决定能不能摸到天花板。后面所有模型，都是在这两个约束下做取舍。

还有一个容易混的词："召回率"（recall）是评估指标，衡量"该被找到的找到了多少"，和"召回层"是两回事。 本章说"三路召回"指链路，说"Recall@100 11.29%"指指标。

A · RECALL召回层：为什么不能"直接上精排"

新手最常见的想法是：既然 DIN 最准，那把 100 万条视频全丢给 DIN 打分不就行了？答案是延迟和成本都不允许，而且没必要。

所以工业界的做法是漏斗式分层：先用几乎不花时间的规则/索引把量级砍下来，再逐层加贵的模型。下面是项目一实际采用的结构，你可以直接对照代码里的四个阶段：

合并去重按 item_id 去重，记录来源路数（后续可做加权）

注意：粗排不是"可选项"。当召回有 5 路、每路 500 条时，精排要打 2500 条，仍然超预算。粗排的存在是为了把"精排的输入条数"压到几十到几百。

一个反直觉的事实：召回阶段追求的是召回率，不是准确率。多路召回里某一路只贡献了 3% 的曝光，但它覆盖了别的路完全捞不到的长尾兴趣——这一路就不能砍。判断标准是"去掉它，Recall@K 掉多少"，而不是"它排得准不准"。

协同过滤：用"和你相似的人"来猜你喜欢

为什么会出现：在深度学习之前，没人能给每个用户训练一个模型。但日志里天然有"谁看过什么"，于是最朴素的想法是——相似的用户喜欢相似的东西。

一句话核心思想：ItemCF 是"你喜欢的物品，和它相似的物品也推荐给你"；UserCF 是"和你相似的人喜欢的物品推荐给你"。

公式：余弦相似度与共现矩阵

sim(i, j) = |N(i) ∩ N(j)| / √( |N(i)| · |N(j)| ) N(i) = 对物品 i 产生过行为的用户集合。分子是共现人数，分母做归一化，防止热门物品因为"跟谁都共现"而通吃。

把"用户 × 物品"的交互写成矩阵 R（行是用户、列是物品，有行为记 1），那么 RᵀR 的非对角元素就是共现次数矩阵，这就是"共现矩阵"这个词的来源。实际工程里没人真的去算这个稠密矩阵——5000 个物品就是 2500 万个格子，20 万物品根本存不下。

四个必须知道的工程细节

① 热度惩罚（最常见的新手坑）

用原始共现次数，热门视频会和所有视频都"高相似"。项目一里有 50% 头部视频只占 3.15% 的曝光份额概念上的反向问题——如果按曝光算相似度，头部会吸走全部推荐位。做法：分母用 |N(i)|^α（α 取 0.5~1），或对活跃用户的行为除以 log(1+n)。

② 倒排索引而不是相似度矩阵

在线不能遍历所有物品算相似度。离线把"物品 → TopK 相似物品 + 分数"存成 KV，在线对用户最近 50 个行为查 50 次表、累加分数，复杂度从 O(物品数) 降到 O(50×K)。

③ 离线算 + 在线查表

相似度是"物品属性"级别的慢变量，每天全量重算一次、增量按小时更新即可。用户侧只保留最近行为做加权。这样在线成本几乎为零，是 ItemCF 至今仍在生产环境跑的原因。

④ 冷启动直接失效

新物品没有任何用户行为 → N(i) 为空 → 与所有物品相似度为 0；新用户没有行为 → 无从查起。所以 ItemCF 必须配一路热门/内容召回兜底，否则新内容永远起不来。

在系统里的位置：召回层的一路，通常排在"热门"之后、"双塔"之前。它擅长挖关联购买/关联观看（看完 A 看 B），不擅长表达"用户长期兴趣"。

UserCF 为什么现在很少用

UserCF 需要维护"用户 → 相似用户"的关系。用户量级通常是物品的 10 倍以上，且用户兴趣漂移快、相似关系每天失效，存储和更新成本都高；更致命的是新用户没有相似邻居。它只在物品少、用户多、时效性强的场景（早期新闻推荐）有优势。记住这个判断即可，不必背公式细节。

坑：把 ItemCF 的相似度直接当排序分用。ItemCF 分数没有概率含义，不可校准，也没法和其他路召回的分数比较大小。正确做法是各路召回只负责"给候选"，分数只用于路内截断；跨路比较交给粗排/精排模型。

向量召回：把"匹配"变成"算内积"

为什么会出现：ItemCF 只能利用"共同行为"这种极稀疏的信号，没法把用户年龄、内容分类、文本语义放进去；而且它本质是查表，不能泛化到没共现过的组合。双塔把用户和物品各编码成一个向量，让"兴趣匹配"变成一次内积。

一句话核心思想：分别用两个独立的塔把用户和物品映射到同一个 k 维空间，用向量内积近似"这个用户会不会点这个物品"。

结构：用户塔 / 物品塔

关键约束：两塔在算出向量之前不能互相看见。所以物品向量可以离线算好、进向量库；用户向量在线算一次。这是双塔能扛住千万级候选的唯一原因，也是它表达力上限的来源。

训练目标：softmax 还是点估

两种主流写法，区别在于"把召回当分类还是当回归"：

点估（pointwise）：L = −Σ [ y·log σ(u·v) + (1−y)·log(1−σ(u·v)) ] 就是普通 CTR 的交叉熵。实现简单，但只告诉模型"这条正样本要好"，没告诉它"在几百万候选里要好"。
全库 softmax（sampled softmax）：L = −log( exp(u·v⁺ / τ) / Σj∈S exp(u·vj / τ) ) S 是"正样本 + 采样出的负样本"集合，τ 是温度，越小分布越尖。分母里的 j 越多、越接近全库，学到的内积越接近"全域竞争"下的排序。

直观区别：点估相当于训练"这题对不对"，softmax 相当于训练"在一堆选项里选对这个"。后者更贴近召回的评估方式（Recall@K 是相对排序），所以召回通常用 softmax 类目标。

ANN 检索：为什么不能暴力算内积

5000 个物品时暴力算内积是 5000 次乘法，无所谓。但真实场景是千万级物品、每次请求都要算，就必须用 ANN（近似最近邻）。

HNSW 一句话原理：把向量组织成多层"可跳转的图"，上层稀疏用于长距离跳跃，下层稠密用于精细搜索；查询时从顶层贪心走向目标区域，只访问少量节点就能找到近似最近邻。

关键参数（以 Faiss HNSW 为例） M = 32 // 每个节点的邻居数：越大越准，内存和构建时间越高 efConstruction = 200 // 建图时的候选队列长度：越大图质量越好 efSearch = 64 // 查询时的候选队列长度：越大召回越高、延迟越高（可在线调） 经验：efSearch 从 32 提到 128，Recall 可能从 0.90 提到 0.98，但延迟翻 2~3 倍。这是一个可以线上动态调的旋钮，也是"ANN 召回率"这个指标存在的原因。

重要认知：ANN 本身有召回损失。业务说的"召回率 95%"可能指的是 ANN 找回真近邻的比例，不是业务 Recall@K。面试时把这两个概念混在一起，很容易被追问穿。

为什么双塔做不了特征交叉

因为用户塔和物品塔在输出向量之前完全隔离。像"用户年龄 × 物品分类"这种交叉特征，需要在网络中间层就让两边信息相遇，而双塔只有在最后一步做内积时才相遇——表达能力被内积这个形式锁死了。

常见误解："我在用户塔里塞了物品 ID 的 embedding，不就有交叉了？"不行——在线时这个物品 ID 是候选，而用户塔必须只算一次给所有候选共用；把候选塞进用户塔，等于每个候选都要重算一遍用户塔，双塔的工程优势立刻消失。这是"离线指标能涨、上线跑不动"的经典死法。

召回评估：别只看一个数

三个指标必须一起看，因为它们互相牵制：

Recall@K = (命中用户真实交互物品的候选数) / (用户真实交互物品总数) Coverage = (被推荐过的物品数) / (全库物品数) Diversity = 1 − 平均两两相似度（通常用分类分布熵或 item2vec 余弦） Recall@K 衡量"漏没漏"，Coverage 衡量"是不是只推头部"，Diversity 衡量"一次推荐里是不是同质化"。

项目一的实测值很能说明问题：热门召回 Recall@100 是 0.0966，覆盖率只有 0.02（只覆盖 2% 的物品）；ItemCF 覆盖率高达 0.8692，但 Recall@100 只有 0.0412；双塔 Recall@100 0.1129、覆盖率 0.1154。三路各自的最优维度不同，所以它们必须同时存在——这正是"多路召回"的量化依据，不是拍脑袋堆模型。

怎么定 K：K 不是越大越好。K 从 100 加到 500，Recall 可能只涨 2 个点，但下游粗排的输入翻 5 倍、延迟直接超标。工程上的做法是画一条"Recall@K 随 K 的曲线"，找拐点，而不是无脑取大。

B · RANK排序层：每一代模型都在补上一代的窟窿

排序模型的历史不是"越做越深"，而是"每换一次结构，都是为了修一个具体的缺陷"。记住缺陷，比记住结构有用。

2010 之前 LR：把排序变成概率问题

能上线、能解释、能并行。缺点是把特征工程的所有脏活都留给了人。

2014 GBDT + LR：让树来造交叉特征

Facebook 的经典两段式。树负责自动组合，LR 负责给权重。

2010 – 2016 FM / FFM：稀疏特征的第二条路

用隐向量内积表达二阶交叉，参数量从 O(n²) 降到 O(nk)。

2016 Wide & Deep：记忆与泛化分开建模

wide 记规则，deep 学泛化，联合训练。工程上第一次把"深度"带进推荐主链路。

2017 DeepFM：把 wide 换成 FM，端到端

省掉人工交叉，embedding 共享，是很多公司精排的基线。

2018 DIN：让用户行为"看情况"生效

候选不同，历史行为的权重就不同。注意力机制进入推荐。

2019 – 2020 DIEN / MMOE / PLE：建模兴趣演化与多目标

从"预测一个数"变成"同时预测 CTR、CVR、时长，还要处理目标冲突"。

2020 – 2022 双塔粗排 / 复杂精排：算力分层

不是模型创新，是工程约束下的必然分工。

2023 – 生成式推荐 / LLM4Rec：换一种范式，但有边界

把"检索 + 排序"变成"生成 ID 序列"。可讲的空间大，能落地的场景窄。

LR：一切排序模型的基线

为什么会出现：早期排序要解决的是"给定特征，估一个点击概率"，并且必须能在大规模稀疏特征上稳定训练、快速上线、可解释。逻辑回归正好满足全部三条。

一句话本质：把特征线性加权后过一个 sigmoid，输出 0~1 的点击概率；权重就是"这个特征每增加 1，点击的 log-odds 增加多少"。

z = w₀ + Σi wᵢ·xᵢ p = σ(z) = 1 / (1 + e−z) L = −(1/N) Σ [ y·log(p) + (1−y)·log(1−p) ] 训练用 SGD/FTRL。FTRL 的关键是 L1 正则 + 自适应学习率，能让绝大多数稀疏特征的权重恰好为 0，模型体积可控——这是 LR 能在工业界活十几年的直接原因。

在系统里的位置：精排。输入是几十到几百维特征（用户、物品、上下文、交叉），输出 pCTR，再乘 bid 得到 eCPM 排序。

代价：只能表达线性关系。想让它学到"年龄 25–29 且分类是游戏"这类交叉，必须人工造 age×cat 特征。特征组合是组合爆炸的，人工只能覆盖一小部分。

项目一的实测：LR 在独热特征上 AUC 达到 0.8473，比全局均值基线 0.5 高出一大截。这不是 LR 强，而是特征本身有信号（分类、时长、新鲜度、位置都和点击强相关）。这个数字也解释了后面为什么"加深度只涨一点点"——线性部分已经把主要信号吃完了。

GBDT + LR：用树自动造交叉特征

解决 LR 的什么问题：人工交叉特征覆盖不全、维护成本高。GBDT 的每棵树按特征阈值分裂，一条样本落到哪片叶子，本质上就是一组特征组合的离散编码。

一句话本质：用树把连续特征切成分段、把特征组合编码成叶子编号，再交给 LR 学权重；交叉特征的活由树干，模型仍然是线性的。

输入 x → GBDT 的 T 棵树 → 每棵树的叶子编号 one-hot 拼接 → 得到稀疏向量 φ(x) p = σ( wlr · [ x, φ(x) ] ) GBDT 只负责"造特征"，不参与梯度回传到 LR；两段是分开训练的（Facebook 2014 论文的做法）。

代价：① 两阶段不联合优化，树学到的分裂目标（拟合残差）和最终排序目标（AUC/CTR）不一致；② 树的数量、深度、学习率要单独调，且树一旦训练完就固定，新特征进来要重训；③ 叶子 one-hot 维度可能上万，模型体积和内存上涨。

今天还用吗：用，但形态变了。现在常见的是"GBDT 做特征筛选/分桶 + NN 做主体"，或者直接把统计特征（count、rate、分桶）喂给深度模型。纯粹的两段式 GBDT+LR 已经很少见，但它的思想——用树把连续特征切成离散区间，让线性模型能学到非线性——到处都是。

FM / FFM：给稀疏交叉一个可学习的参数

为什么会出现：独热编码后特征极度稀疏。LR 想学 x_age=25 × x_cat=游戏 的权重，但这两个特征同时非零的样本可能只有几十条，权重根本学不出来。FM 的思路是：不直接学"组合的权重"，而是给每个特征一个隐向量，用内积算组合权重。

一句话本质：每个特征学一个 k 维隐向量，任意两个特征的交叉强度 = 两个隐向量的内积；即使某个组合没出现过，只要两个特征各自出现过，内积就有值。

y = w₀ + Σi=1n wᵢ·xᵢ + Σi=1n Σj=i+1n ⟨vᵢ, vⱼ⟩·xᵢ·xⱼ 其中 ⟨vᵢ, vⱼ⟩ = Σf=1k vi,f·vj,f vᵢ 是第 i 个特征的 k 维隐向量。k 通常取 8~32；n 是特征数（独热后可能上万），但每个特征只有一个隐向量，所以参数量是 n×k，不是 n²。

为什么能解决稀疏交叉：组合权重不再是一个独立参数，而是由两个特征的隐向量共同决定。样本里"25 岁"和"游戏"各自出现得多，它们的向量就能学好；两者的内积即使没在训练集里同时出现过，也能泛化出一个合理的分数。这就是"参数共享"带来的泛化。

复杂度怎么从 O(n²k) 降到 O(nk)：朴素计算要枚举所有 (i,j) 对，每对算一次 k 维内积，是 O(n²k)。利用内积的代数恒等式可以整体重写：

Σi=1n Σj=i+1n ⟨vᵢ, vⱼ⟩ xᵢ xⱼ = ½ · [ ( Σi=1n vᵢ·xᵢ )² − Σi=1n vᵢ²·xᵢ² ] 右边先对每个维度累加一次（O(nk)），再平方、再逐元素相减（O(nk)），所以整体 O(nk)。这是 FM 能上工业规模的关键——不是近似，是恒等变形。注意第二项必须逐元素平方，不能用 (Σ vᵢxᵢ)² 减去一个标量。

展开看更清楚：(Σᵢ vᵢxᵢ)² = Σᵢ vᵢ²xᵢ² + 2Σᵢ<j ⟨vᵢ,vⱼ⟩xᵢxⱼ，把对角线项减掉、除以 2，剩下的正好是全部二阶交叉。所以只要算一次"加权向量和"，就能同时得到所有交叉项。

代价：① 只建模二阶交叉，三阶以上的组合仍要靠 DNN 或人工特征；② 每个特征只有一个隐向量，无法区分"和谁交叉"——这正是 FFM 要改进的地方；③ k 要调，k 太小欠拟合、太大过拟合，且推理时要对每个候选算一次 O(nk) 的向量和。

FFM：交叉还要看"跟谁交叉"

FM 里每个特征只有一个向量，无论跟谁交叉都用它。FFM 认为这不合理：年龄 和 分类 交叉、年龄 和 城市 交叉，应该用不同的表示。于是每个特征对每个 field 各学一个向量：

y = w₀ + Σ wᵢxᵢ + Σi Σj≠i ⟨vi, f(j), vj, f(i)⟩ · xᵢxⱼ f(j) 是特征 j 所属的 field。参数量从 n×k 变成 n×F×k（F 是 field 数），表达力更强，但内存和过拟合风险同步上升。

一句话本质：每个特征按"对方属于哪个 field"准备多套隐向量，让同一次交叉的权重能感知交叉的类型，而不是所有交叉共用一套表示。

代价：参数量 ×F，训练更慢、更容易过拟合，且无法用上面的 O(nk) 技巧（因为向量依赖对方 field），只能对 Top 交叉对做裁剪。所以 FFM 常用于 CTR 竞赛和小规模场景，大规模在线系统里 FM/DeepFM 更常见。

Wide & Deep：记忆和泛化，两条腿走路

为什么会出现：FM 只有二阶交叉，GBDT+LR 是两段式。Google 2016 年的想法是：wide 部分记住"哪些组合历史上有效"（记忆），deep 部分泛化到没见过的组合（泛化），两者联合训练。

一句话本质：一个线性"记忆器"加一个深"泛化器"，输出相加、梯度共享，让模型既有规则兜底又能探索。

y = σ( wwide·[x, φ(x)] + wdeep·a(L) + b ) φ(x) 是人工交叉特征（如"已安装 App × 曝光 App"），a(L) 是 deep 最后一层隐层。两部分梯度一起回传。

解决了什么：纯 deep 对稀疏组合容易过拟合、泛化过头（推荐一堆"相关但没用"的东西）；纯 wide 只能记住见过的组合。联合后，wide 保证"确定性规则"不丢，deep 保证"探索"能力。

代价：wide 部分仍然要人工设计交叉特征——这恰恰是后面 DeepFM 要解决的。另外两部分学习率要分别调，训练不稳定是常见问题。

DeepFM：把 wide 换成 FM

解决 Wide&Deep 的什么问题：wide 部分的人工交叉特征。DeepFM 用 FM 替换 wide，且 FM 和 deep 共享同一套 embedding，端到端训练，不再需要特征工程。

一句话本质：FM 负责低阶交叉、DNN 负责高阶交叉，两者共享同一份 embedding 表，一次训练同时拿到两种表达能力。

ŷ = σ( yFM + yDNN ) yFM = w₀ + Σ wᵢxᵢ + Σi<j ⟨vᵢ, vⱼ⟩xᵢxⱼ yDNN = MLP( concat(e₁, e₂, …, em) ) 关键细节：FM 的一阶项、二阶项和 DNN 共用同一份 embedding 表。共享的好处是低频特征也能从 DNN 侧拿到梯度，缓解稀疏。

为什么它成了基线：结构简单、不需要人工交叉、能同时学低阶和高阶、训练稳定。在多数中等规模场景里，DeepFM 已经能拿到 80% 的收益。

坑：把 DeepFM 的 FM 部分当成"可选的装饰"。如果去掉 FM、只留 DNN，在稀疏特征上往往掉点明显（尤其是长尾物品）。因为 DNN 对稀疏 ID 特征的学习效率远低于显式的二阶内积。项目一里 FM 单独就有 0.8501，DeepFM 只到 0.8520，说明低阶信号占大头。

DIN：用户的兴趣，取决于你推荐什么

为什么会出现：DeepFM 把用户历史行为做 embedding 后 sum pooling 成一个固定向量。问题在于，这个向量和候选物品无关——不管候选是"篮球"还是"美妆"，用户的历史兴趣表示都一模一样。但真实情况是：用户历史里既有篮球也有美妆，推荐篮球时应该多看篮球行为，推荐美妆时应该多看美妆行为。

一句话本质：用候选物品给用户历史行为做注意力加权，让"用户表示"随候选变化。

vu(A) = Σj=1H a(ej, ea) · ej a(ej, ea) = exp( MLP([ej, ea, ej ⊙ ea]) ) / Σk=1H exp( MLP([ek, ea, ek ⊙ ea]) ) e_j：第 j 条历史行为的 embedding；e_a：候选物品 embedding；⊙：逐元素乘；H：行为序列长度。注意力分数在序列维度上做 softmax，所以权重和为 1。

对应到 attention 的三个角色，DIN 的映射非常清晰：

角色在 DIN 里是什么直觉
Query（查询）候选物品的 embedding e_a"我现在在考虑推这个，你看看像不像他喜欢的"
Key（键）历史行为的 embedding e_j每条历史行为用来"应答"的凭证
Value（值）历史行为的 embedding e_j 本身加权求和后构成用户兴趣向量

为什么要对历史行为做注意力：因为用户兴趣是多峰的。一个用户可能既看健身也看美食，但这次候选是减脂餐，健身行为的相关性更高。sum pooling 把两个峰平均掉，等于告诉模型"他一半时间在健身、一半时间在吃"，对哪个候选都不精准。注意力相当于每次都重新组织一遍历史，只留下和当前候选相关的部分。

工程细节：① 行为序列要做截断（通常最近 50~200 条），太长的序列延迟扛不住；② 需要用 mask 处理变长序列，padding 位置的注意力分数要置为 −∞；③ 序列里要带"行为类型 + 时间差"的 embedding，否则无法区分"刚看过"和"半年前看过"；④ 线上要做行为序列的实时拼接（用户刚点完下一个请求就要看到），这是特征服务最容易出问题的地方。

代价：注意力是逐候选计算的。100 个候选 × 50 条行为 × 一个小 MLP，计算量比 DeepFM 高一个量级，通常只能在精排（几十到几百候选）用，不能下放到召回。另外序列长度不足时（项目一人均序列 1.16），注意力几乎退化成"取最近一条"，涨点有限。

项目一的实测对比很诚实：DeepFM 0.8520 → DIN 0.8584，只涨了 0.0064。原因就是行为序列太短（人均点击 1.16 次），DIN 的注意力没有足够的历史可供"选择"。但这 0.0064 依然稳定（6 个 epoch 的曲线单调上升），说明结构本身有效，只是数据供给不足。模型和数据的匹配，比模型是否先进更重要。

DIEN 与多任务：从"预测一个数"到"同时预测几个数"

DIEN：兴趣不只有强弱，还有演化

DIN 只对历史行为做加权，没有建模"兴趣随时间怎么变"。DIEN（2019）先用 GRU 把行为序列编码成隐状态序列，再用 AUGRU（带注意力的 GRU）让候选物品决定"在演化的哪一步停下"。一句话：DIN 看兴趣的分布，DIEN 看兴趣的轨迹。

代价：序列模型训练慢、线上只能增量推理，且对序列长度更敏感。序列短于 5 条时，DIEN 相对 DIN 几乎没有收益，工程复杂度却翻倍——这是典型的"论文有效、业务不划算"。

多任务：为什么不能把 CTR 和 CVR 分开训

广告和电商场景要同时预测点击率（CTR）和转化率（CVR），排序公式通常是 eCPM = bid × pCTR × pCVR。看起来可以训两个独立模型，但 CVR 模型有一个致命问题：CVR 的训练样本只有"点击过"的样本，因为只有点击后才可能转化。这带来两个偏差：

样本选择偏差（SSB）

模型在"点击样本"上训练，却在"全量曝光样本"上预测。点击样本是经过 CTR 模型筛选过的有偏子集，分布和全量不一致。

数据稀疏（DS）

点击样本本来就少（项目一 CTR 13.82%），转化更少。单独训 CVR 模型，参数根本学不充分。

ESMM 的解法：不直接学 pCVR，而是学 pCTCVR = pCTR × pCVR，并在全量曝光样本上训练。两个子网络共享 embedding，CVR 分支只在点击样本上算损失，但梯度可以通过共享底层从全量样本里获得信息。

pCTCVR = pCTR × pCVR L = Σ曝光样本 LCTR(yclick, pCTR) + Σ曝光样本 LCTCVR(yclick&convert, pCTCVR) 关键：两个损失都在全量曝光空间上算。y_click&convert 表示"既点击又转化"，没有点击的样本这一项为 0，但仍然参与 pCTCVR 的损失计算——这就是它绕开样本选择偏差的方式。

注意一个细节：ESMM 输出的是 pCTR 和 pCTCVR，真正的 pCVR 要用两者相除得到，这个除法在 pCTR 很小时可能数值不稳定，实践中要加保护。

MMOE 与 PLE：多目标之间的"跷跷板"

多任务最怕的是负迁移：优化 CTR 把 CVR 搞差了。原因是所有任务共享同一个底层，任务之间互相抢参数。

MMOE：yk = hk( Σi=1E gk,i(x) · experti(x) ) PLE ：yk = hk( concat[ gk(x) ⊙ {expertk,j}, gk(x) ⊙ {expertshared,j} ] ) g_k 是第 k 个任务的 gate（softmax 输出权重）。MMOE 所有任务共享同一组 expert，只是权重不同；PLE 在此之上给每个任务留了"专属 expert"，只让共享 expert 承担共性。
对比MMOEPLE
专家池全部共享，任务用 gate 选择共享专家 + 每个任务专属专家
解决的问题硬共享导致的负迁移MMOE 在任务相关性低时仍会互相干扰（seesaw）
参数/复杂度较低较高，专家数随任务数增长
适用任务相关性中等、算力紧任务差异大（如点击 vs 长时间观看）

坑：多任务不是"多预测几个目标就一定涨"。如果两个任务的相关性很低（比如"点击"和"举报"），强行共享底层会让两个任务都变差。上线前必须做单任务 vs 多任务的 A/B，并检查每个任务的 AUC 是不是都掉了。

生成式推荐：能讲什么，不能吹什么

2023 年之后最热的方向。核心思路是把"召回 + 排序"改写成序列生成：先把每个物品量化成一个短 ID（semantic ID，比如用 RQ-VAE 把内容向量逐层量化成 3 个 token），再训练一个 seq2seq 模型，输入用户历史，自回归地生成下一个可能被点击的物品 ID。

P(it+1 | i1, …, it) = Πc=1C P( tokenc | i1, …, it, token<c ) C 是一个物品被拆成的 token 数（常见 3~4）。生成过程是逐 token 的，所以一个物品需要 C 次前向；这也是它延迟高的根本原因。

它确实解决了一个真问题：传统召回把"用户兴趣"压成一个向量，而生成式模型可以表达"多峰兴趣 + 序列依赖"，并且理论上一个模型替代多路召回。但边界必须讲清楚：

边界具体表现工程含义
物品必须"已入词表"新物品要先算语义 ID，模型才能生成它新品冷启动依赖 ID 映射的更新频率，做不到分钟级
解码延迟高逐 token 生成，一个候选 C 次前向；要出 100 个候选就是几百次很难塞进 100ms 预算，通常只能做"少量候选"或离线
目标不对齐训练目标是"下一个物品的似然"，不是 CTR / 时长 / 多样性需要额外的排序模型和重排兜底，不能端到端替代
可控性差生成结果难保证"不含违规内容""同创作者不超过 2 条"合规、频控、打散仍然要靠规则层
评估口径变了输出是序列，不是分数；Recall@K 要重定义离线指标和现有链路不可直接比较，A/B 成本高

别吹的版本："我们用它替代了整条召回排序链路。"能落地的版本："我们用 semantic ID + 生成式模型做了一路补充召回，离线 Recall@100 提升 X%，线上作为其中一路参与融合；延迟从 8ms 涨到 25ms，所以只放在非高峰或预生成。"——后者才是 2024–2025 年多数公司的真实状态。

C · COARSE & RERANK粗排与重排：夹在中间的工程妥协

粗排：为什么需要一个"不准但很快"的模型

假设召回合并后 2000 条候选，精排单条 0.8ms，就是 1.6 秒——预算是 60ms。粗排要做的是用 0.02ms/条 的成本，把 2000 条砍到 300 条，同时保证"砍掉的里面没有太多用户会点的"。

常见做法有三种，本质都是"减少计算量"：

做法怎么省代价
复用双塔向量，只算内积物品向量离线算好，在线一次内积；可加少量交叉特征精度明显低于精排，只能做粗筛
轻量 LR / GBDT + 少量特征特征少、无 GPU、可批量向量化吃不到行为序列和高阶交叉
精排模型蒸馏到小模型用精排的打分当 soft label，小模型学排序需要额外训练链路，蒸馏目标要选对（pointwise 还是 pairwise）

粗排的核心矛盾：它和精排的目标一致（排序），但约束完全不同（延迟）。所以粗排的评估不能只看 AUC，要看 Top-N 保留率：精排 Top100 里有多少被粗排留下来了。这个指标比 AUC 更贴近它的实际职责。

重排：分数高不代表该排在前面

精排给每条候选一个分数，但如果直接按分数排序，会出现三个问题：① 前 10 条全是同一个创作者；② 全是同一类内容，用户很快疲劳；③ 违反业务规则（违规内容、已下架、频控）。重排就是在这三步上做修正。

多样性：MMR 公式

MMR（Maximal Marginal Relevance）是"相关性"和"多样性"的加权折中。每选一个物品，都要扣掉它和已选集合的相似度：

MMR = argmaxDi ∈ R \ S [ λ · Sim1(Di, Q) − (1 − λ) · maxDj ∈ S Sim2(Di, Dj) ] R：候选集；S：已选集合；Sim₁：候选与用户/查询的相关性（通常用精排分归一化）；Sim₂：候选之间的相似度（同分类=1，不同分类按 embedding 余弦）；λ ∈ [0,1] 控制偏向相关性还是多样性。

λ=1 时退化成纯按分数排序；λ=0.7 时，一个分数很高但和已选内容重复的物品，会被"惩罚"到后面。工程上 Sim₂ 不用真的算 embedding 余弦，用"分类相同 / 创作者相同 / 标签重合度"这种便宜特征就够了。

# 重排：MMR + 打散 + 业务规则（简化伪代码）
selected = []
while len(selected) < 10:
    best, best_score = None, -1e9
    for it in candidates:
        if violated(it):                      # 频控 / 已下架 / 黑名单
            continue
        rel = norm_score[it]
        dup = max([sim(it, s) for s in selected] or [0])
        mmr = lam * rel - (1 - lam) * dup
        if same_creator(it, selected[-2:]) or same_cat(it, selected[-2:]):
            mmr -= 0.15                       # 打散惩罚：相邻两位不重复
        if mmr > best_score:
            best, best_score = it, mmr
    selected.append(best)
    candidates.remove(best)

打散规则通常是硬约束，不进 MMR 的软分数：同一创作者最多 2 条、同分类不相邻、前 3 位必须覆盖至少 2 个分类。业务规则优先级最高：置顶、强插、频控（同一内容 24 小时内不重复曝光）、合规过滤。流量调控则是从平台视角干预：给新内容保底曝光、给长尾内容配额、给商业化内容插槽。

坑：重排的规则叠加太多，会互相打架。真实项目里出现过"打散要求相邻不同类"+"运营要求前 3 位必须有两个活动位"+"频控要求 24 小时不重复"同时生效，结果候选池被过滤到不足 10 条，接口直接返回空列表。规则必须分层 + 兜底：硬规则先过滤，软规则只扣分不淘汰，最后一定要有"不足时放宽"的降级逻辑。

D · TRAINING训练与调优：模型之外，决定成败的部分

同一个 DeepFM，两个人训出来的 AUC 可能差 0.02——比换模型带来的差异还大。这一节讲的全是不写进论文、但每天都在踩的东西。

损失函数：你优化的目标，决定了模型学成什么样

损失形式适合什么副作用
LogLoss（交叉熵）−[y·log p + (1−y)·log(1−p)]需要概率值（eCPM 要乘 bid）被大量简单负例主导，排序区分度不一定最好
加权 LogLoss−Σ wᵢ·[…]样本重要性不同（时长、转化）权重不当会让预测概率整体偏移，必须重新校准
Pairwise / BPR−log σ(s⁺ − s⁻)只关心相对顺序（召回、粗排）输出不是概率，不能直接进 eCPM
Focal Loss−α(1−p)^γ·log p极不平衡（转化率 <1%）会破坏校准，需要单独做概率校准

一个真实的选择：短视频推荐里"点击"不等于"满意"，完播和点赞更能代表目标。常见做法是把标签做成加权：点击=1、完播再+1、点赞+2，或者直接用播放时长做回归。项目一里完播率 57.3%、点赞率 12.64%，如果只优化点击，模型会偏向"标题党"——完播和点赞信号必须进损失或进多任务。

样本权重与样本构造

  • 曝光未点击是负样本，这没错；但"曝光了 0.1 秒就划走"和"看了 20 秒没点"不是同一种负例，有权重差异。
  • 位置偏差：第 1 位 CTR 15.28%、第 4 位 12.59%，差 2.7 个百分点。这个差异是"位置"造成的，不是内容更好。训练时可以给低位置样本更高权重，或用位置作为特征 + 线上置 0 做 debias。
  • 重复曝光：同一用户 24 小时内看到同一内容多次，只保留第一次作为样本，否则正负样本都会被重复计入，模型过拟合"热门"。
  • 时间切分：绝不能随机切分。用第 1–24 天训练、第 25–30 天测试，才能模拟"用过去预测未来"。

过拟合与正则

推荐模型的过拟合和 CV 任务不太一样：它往往不是"记住训练集"，而是记住热门物品和活跃用户。表现是训练 AUC 0.90、测试 0.85，且推荐结果高度集中在头部。

有效的做法

  • Embedding 加 L2 正则（比全连接层更重要）
  • Dropout 放在 embedding 之后、隐层之间
  • Early stopping：看验证集 AUC，不看训练 loss
  • 低频特征做频次截断（出现 < 5 次归为 UNK）

看似有效其实没用

  • 只加 BatchNorm：小 batch 下反而更不稳定
  • 把 embedding 维度调到 256：参数暴涨，稀疏特征更学不动
  • 用 AUC 早停但不看 LogLoss：模型可能过度自信
  • 在测试集上反复调参：这本身就是过拟合

Embedding 维度怎么选

经验规则不是"越大越好"，而是和数据密度匹配：

d ≈ k · (类别数)1/4，实践区间 8 ~ 64 项目一的物品只有 5000 个、曝光 31.8 万条，每个物品平均 63 次曝光，k 取 32 已经足够；把 d 提到 128，参数量 ×4，AUC 反而可能掉。真正需要大维度的是"物品数千万、每条样本都能贡献梯度"的场景。

③ 召回 Recall@100：双塔最好，但 ItemCF 输给热门

先解释"为什么 LR 已经 0.847，DIN 只涨到 0.858"。三个原因叠加：

信号以低阶为主

分类（搞笑 25.07% vs 萌宠 6.86%）、新鲜度（当天 15.95% vs 30 天前 10.74%）、位置（第 1 位 15.28% vs 第 4 位 12.59%）——这些都是一阶或简单交叉特征，LR 用独热就能吃掉。深度模型能加的主要是"高阶组合"，而这部分在仿真数据里本来就弱。

序列太短，DIN 没料可用

人均点击 1.16 次，意味着大部分用户的行为序列只有 0 或 1 条。DIN 的注意力机制需要"多条历史里挑相关的"，序列长度为 1 时，注意力权重恒为 1，退化成 DeepFM。它能涨 0.0064，已经算超常发挥。

AUC 接近这份数据的上限

标签由"兴趣匹配 + 位置加成 + 随机噪声"生成，本身有不可约的随机性。0.85 左右已经是这份仿真数据的信息上限，再深的模型也只能拟合噪声。真实业务里如果 AUC 卡在 0.8，先怀疑特征，不要怀疑模型深度。

再解释"为什么 ItemCF 反而低于热门"。这是本章最值得记住的一个反例：

热门：Recall@100 = 0.0966，Coverage = 0.0200 ItemCF：Recall@100 = 0.0412，Coverage = 0.8692 双塔：Recall@100 = 0.1129，Coverage = 0.1154 Coverage 的定义是"被推荐过的物品数 / 全库物品数"。ItemCF 覆盖了 86.92% 的物品，热门只覆盖 2%——但 Recall 差了 2.3 倍。

原因不复杂：人均交互只有 1.16 次，共现矩阵极度稀疏。ItemCF 靠"两个物品被同一批人看过"来建立相似度；一个人平均只点 1.16 条，绝大多数物品对根本没有共现，相似度为 0 或来自偶然的一次共现。于是 ItemCF 只能靠零星信号把候选摊到全库（覆盖率 86.92% 就是这么来的），但摊得越开、命中真实兴趣的概率越低。

热门召回则相反：它只推 2% 的头部内容，而这份数据里头部内容的 CTR 本来就高（搞笑 25.07%、美食 21.76%），用户兴趣也集中在这些类目上，所以"无脑推热门"的命中率反而更高。双塔能赢，是因为它用内容特征和用户特征做了泛化，绕开了"必须共现"这个限制。

这个反例的通用价值：个性化模型不一定赢过强基线，尤其是在交互稀疏的数据上。所以做召回的第一件事不是上双塔，而是先量一下：人均交互多少？物品覆盖分布长什么样？如果人均 < 2 次，先把热门、内容标签、语义召回做扎实，再谈协同过滤和向量召回。

F · PITFALLS七条常见误区，每一条都有人栽过

误区 1：模型越深越好。这句话在 CV/NLP 里接近正确，在搜广推里经常是错的。项目一的证据很直接：LR 0.8473 → DIN 0.8584，换了三代模型，只换来 1.11 个点；而把"热门召回"换成"双塔召回"，Recall@100 从 9.66% 提到 11.29%，涨了 16.9%（相对值）。在特征和样本没做好的时候，换模型是性价比最低的动作。而且深模型带来的是延迟、内存、部署复杂度三倍上涨。

误区 2：把 AUC 当唯一指标。AUC 只看排序，不看概率大小。DIN 的 AUC 最高（0.8584），但它的预测均值 0.1527 比真实 CTR 0.1378 高 10.8%——如果直接拿这个 pCTR 去算 eCPM，出价会被系统性高估。广告场景必须同时看 LogLoss 和校准曲线；内容场景还要看人均时长、完播率、多样性，因为 AUC 涨了但推荐全是同一类内容，用户体验是下降的。

误区 3：召回和排序用同一套评估。召回看 Recall@K / 覆盖率，排序看 AUC / LogLoss / 校准，重排看多样性 / 打散满足率。拿 AUC 去评估召回是错的——召回模型输出的是内积分数，不是概率，AUC 没有业务含义；反过来，用 Recall@K 评估精排也没有意义，因为精排的输入已经被截断了。每一层用自己的指标，且要能串起来解释最终业务指标。

误区 4：忽略负样本的定义。什么是负样本，直接决定模型学什么。"曝光未点击"是负样本，但"曝光了但用户根本没看到（在屏幕外）"不该算负样本；"点了但立刻退出"算正样本还是负样本？E-commerce 里"下单未支付"算不算转化？这些问题没有标准答案，但必须写进文档、和业务对齐、并在特征和损失里体现。项目一人均点击 1.16 次，如果再把"曝光未点击"随意下采样，正负比会彻底失真，模型输出的概率就没法用。

误区 5：离线涨了就直接上线，不做 A/B。离线 AUC +0.003 在统计上可能不显著，线上可能因为延迟增加 5ms 导致整体指标下降。正确流程是：离线 AUC + 校准 + 分天稳定性 → 小流量 A/B（看核心指标和护栏指标）→ 扩量。A/B 的样本量要提前算，不能跑两天看着"涨了"就全量。

误区 6：多路召回，路越多越好。每加一路都会带来过滤成本、去重逻辑、分数融合的复杂度。判断标准是边际 Recall 增益：加这一路，Recall@K 涨了多少？如果只涨 0.3%，但它贡献了大量重复候选和线上耗时，就该砍。项目一里三路召回各有明确的定位（兜底 / 长尾覆盖 / 个性化），不是因为"别人都有"才加的。

误区 7：离线指标异常高，先庆祝再上线。AUC 突然从 0.85 跳到 0.95，第一反应应该是"我是不是用了未来信息"，而不是"我的模型真强"。最典型的特征穿越：用"视频 7 日 CTR"预测第 3 天的点击；用"订单最终状态"预测下单；用全量统计的归一化参数处理训练样本。上线前逐个特征问一遍"这个值在样本产生的那一刻算得出来吗"，能省掉一次事故。

Q1：为什么召回和排序必须分成两层？只用精排模型对全库打分不行吗？

三层原因：①量级——全库 105~107，精排单条 0.8ms，光计算就要几百秒，而接口预算只有 100ms；②模型形态——精排要吃行为序列、交叉特征，这些特征必须"逐候选"拼接，无法预先算好；召回用双塔可以离线算物品向量、在线算一次用户向量，成本差几个数量级；③目标不同——召回要"别漏"（Recall@K），排序要"排得准"（AUC/校准），用同一个模型同时优化两个目标会互相拖累。

可以只用一个模型的特例：候选量很小（比如几千条）且延迟宽松的场景，可以直接用精排打分，但工业界主流内容/电商场景都不成立。

Q2：FM 的公式是什么？它为什么能处理稀疏特征，复杂度怎么从 O(n²k) 降到 O(nk)？

y = w₀ + Σwᵢxᵢ + ΣΣ<vᵢ,vⱼ>xᵢxⱼ，其中 <vᵢ,vⱼ> = Σ_f v_{i,f}·v_{j,f}。

稀疏场景下，组合 (i,j) 的样本可能只有几十条，独立权重学不出来；FM 用两个特征的隐向量内积表示组合权重，参数共享让"25 岁"和"游戏"各自的向量能从所有相关样本里学习，即使两者从未共现也能泛化。

复杂度：朴素枚举 (i,j) 是 O(n²k)。用恒等式 Σ_{i<j}<vᵢ,vⱼ>xᵢxⱼ = ½[(Σvᵢxᵢ)² − Σvᵢ²xᵢ²]，先算一次加权向量和（O(nk)），再逐元素平方相减（O(nk)），整体 O(nk)。注意是恒等变形，不是近似；第二项必须逐元素平方。

Q3：DIN 的 attention 里，query、key、value 分别是什么？为什么不能像 DeepFM 一样对行为做 sum pooling？

query = 候选物品 embedding e_a；key = 历史行为 embedding e_j；value 也是 e_j（所以是 self-attention 的变体，key 和 value 同源）。打分函数是 MLP([e_j, e_a, e_j⊙e_a])，在序列维度上 softmax 得到权重，加权求和得到用户表示 v_u(A)。

sum pooling 得到的是固定向量，与候选无关；但用户兴趣是多峰的（既看健身也看美食），推荐减脂餐时应该更关注健身行为。注意力让用户表示随候选变化，这是 DIN 的增量。代价是每个候选都要算一遍，成本高，只能在精排用。项目一人均序列 1.16 次，注意力退化成取最近一条，所以只涨 0.0064。

Q4：ESMM 解决什么问题？MMOE 和 PLE 的区别是什么？

ESMM 解决 CVR 建模的两个偏差：样本选择偏差（CVR 只能在点击样本上训练，却要在全量曝光上预测）和数据稀疏（点击样本本来就少）。做法是不直接学 pCVR，而是学 pCTCVR = pCTR × pCVR，在全量曝光样本上同时算 CTR 和 CTCVR 两个损失，两个子网络共享 embedding。

MMOE：所有任务共享同一组 expert，每个任务用各自的 gate 做 softmax 加权，缓解硬共享的负迁移。PLE：在 MMOE 基础上增加"任务专属 expert"，只让共享 expert 学共性，进一步缓解任务相关性低时的 seesaw（一个任务涨、另一个任务跌）。代价是参数量随任务数增长。

Q5：离线 AUC 从 0.847 涨到 0.858，线上却没涨，你会按什么顺序排查？

按"最可能且最容易验证"排序：①特征穿越——逐个特征核对时间戳，确认样本产生时该特征可算；②链路不一致——抽样比对离线/线上同一 key 的特征值，尤其是实时特征；③位置偏差——训练时带位置特征，线上重排后位置分布变了，模型失效；④样本偏差/分布漂移——按天看 AUC，看训练集 item 分布和线上曝光分布是否一致；⑤指标口径——离线算 AUC 的样本集和线上考核口径是否一致（是否含重复曝光、是否只算点击样本）；⑥统计显著性——A/B 样本量够不够，0.003 的提升可能只是噪声。

补充一个容易被忽略的：延迟增加。新模型慢 10ms 导致超时降级，实际效果会被链路吃掉，指标自然不涨。
