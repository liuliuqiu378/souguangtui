BACKGROUND业务背景：三个问题，一个目标

这是一个"首页推荐"项目，不是推荐中台。范围划得越窄，越能把每一步讲清楚。

「抖风」是一个短视频产品（仿真设定），首页是唯一的流量入口。改造前，首页由运营配置的热门榜驱动： 所有人看到同一批视频，按近 7 天点击量排序。数据里能看到三个具体症状：

新用户留不住

新用户（注册 < 7 天）的 CTR 是 14.68%，反而高于老用户的 13.82%。 但点击多不等于满意——热门内容对新用户是"看起来热闹、和他没关系"，点完就走。缺的是兴趣匹配，不是曝光量。

老用户消费不深

点击之后只有 57.3% 完播、12.64% 点赞。人均历史点击序列长度仅 1.16 条， 说明大量曝光没被点开，点开的内容也没能形成连续消费。

内容池长尾

曝光量后 50% 的视频只拿到 30.05% 的曝光，是其数量占比的 0.6 倍。同时头部 1% 内容拿到 3.15% 曝光。 热门榜把"分发"变成了"再分配头部"。

指标体系：北极星只有一个

短视频的核心不是"点了多少"，而是"看了多久"。所以北极星指标定为人均有效播放时长， CTR 只是过程指标——CTR 涨、时长短，是典型的标题党，必须在复盘里拆开看。

这次要解决的问题，写死一句话：把首页推荐从"热门排序"升级为"个性化排序"，在曝光总量不变的前提下， 目标 CTR 相对 +8%、人均有效播放时长相对 +5%，同时把内容覆盖率从 2% 提到 10% 以上。

明确不做：直播推荐、搜索、广告变现、多目标融合的线上实现。范围外的东西只在"如果真实上线"一节里说明。

为什么先做排序、不先做召回？因为改造前根本没有"召回"这个概念——所有人看同一个热门榜。 热门榜本身就是一路覆盖率极低的召回。先补召回，精排才有东西可排；只换精排模型，收益会被候选集的同质化吃掉。 这个判断在后面被数据验证：热门的覆盖率只有 2%。

4）数据是怎么生成的：因果结构，而不是随机数

生成脚本的核心是一个隐变量模型。用户有一个 8 维偏好向量 pref，每条视频有一个 8 维主题向量 item_vec，点击概率由两者的内积、品类匹配、年龄先验、时长匹配、质量、时效、重复曝光、 位置偏差共同决定。关键代码（已精简）：

dot  = np.sum(pref[u] * item_vec[items], axis=1) / math.sqrt(K)   # 兴趣匹配
logit = (-6.15
         + 2.15 * dot                                  # 个性化主信号
         + age_cat_aff[age[u], cat[items]]              # 年龄 × 品类先验
         + 0.72 * same0 + 0.40 * same1                  # 主/次兴趣匹配
         + 0.55 * (dur_bucket[items] == dur_pref[u])    # 时长偏好
         + 0.9  * (quality[items] - 0.5)                # 内容质量
         + 1.1  * np.exp(-fresh_days[items] / 12.0)     # 时效衰减
         + repeat                                       # 历史同品类点击次数 × 0.5
         + np.array([0.62, 0.34, 0.16, 0.0])[pos - 1]   # 位置偏差
         + quality_sens[u] * 0.5 * (quality[items] - 0.5)
         + RNG.normal(0, 0.32, n))                      # 不可解释噪声
p     = 1 / (1 + np.exp(-logit))
click = (RNG.random(n) < p).astype(int)

点击之后的完播、点赞是条件概率，由内容质量和时长决定，与用户无关：

finish_p = clip(0.42 + 0.42·quality − 0.055·duration_bucket + ε, 0.05, 0.97)
like_p   = clip(0.035 + 0.16·quality + ε, 0.005, 0.5) 所以"点击但没完播"不是数据缺失，而是这条内容本来就更容易被划走——这一点决定了多目标建模的可行性。

这三个设计决定了项目"能讲出东西"：

仿真机制对应的真实业务对建模的影响
用户向量 × 内容向量（权重 2.15）兴趣匹配个性化真的有效，双塔/DIN 有可学信号，不是纯噪声
曝光按 pop ∝ exp(1.6·quality + 0.55·log(creator_heat) − fresh/60) 采样线上流量本身偏向头部样本选择偏差：模型只见过被曝光的内容，热门召回的离线指标会被"喂"得偏高
位置 1–4 的固定加成 [0.62, 0.34, 0.16, 0]首位偏差位置特征进模型会学到一个"线上会变"的规律，必须固定基准位或做 debias
时效衰减 exp(−days/12)内容冷启动与新鲜度新鲜度是一个真实有效特征，但也让"老内容"在训练集里被系统性低估
噪声 σ=0.32用户行为的随机性AUC 有天花板（不会到 0.99），0.85 左右是这份数据的合理水平
完播/点赞是点击后的条件概率多目标、多任务不能把全量曝光的 finish 当二分类样本，否则负样本定义就错了

为什么这套数据能"学到东西"？因为 label 是特征的函数：给定 (用户兴趣, 内容品类, 质量, 时效, 位置)， 点击概率有稳定的条件分布。模型只要能从特征里恢复出 dot 和品类匹配，AUC 就会显著高于 0.5。 同时噪声保证它不会变成"背答案"——这也是我敢把 AUC 0.8584 写出来的原因。

5）数据探查：5 张图，每张都要能说出一句话

下面所有图表的数据都来自 data/p1_metrics.json 的 charts 字段，由脚本直接从日志聚合， 没有一处是手工填的。图下面那句话才是重点——面试时讲图，讲的是结论。

这张图告诉我们：品类之间的点击率差近 3.7 倍（搞笑 25.07% vs 旅行/萌宠 6.86%）， 但曝光量也差了近 3 倍（40,419 vs 12,093/14,842）。所以品类 CTR 是"内容供给 × 受众规模"的混合结果， 直接把它当用户偏好会过拟合。正确用法是 用户兴趣 × 品类 的交叉特征，而不是单独一个品类 id。

这张图告诉我们：第 1 位 15.28%、第 4 位 12.59%，首位相对末位高 21.4%， 而内容本身没有变。这就是位置偏差：日志里的"点击"同时包含了"内容好"和"位置好"两种原因。 把它当纯 label 学，模型会高估"排在前面的内容"，上线后一旦换排序，预估立刻失准。

这张图告诉我们：曝光到点击只留下 13.82%，点击到完播 57.3%，完播到点赞 22.1%（5,555 / 25,174）。 最大的流失在"曝光→点击"，但这不代表只优化 CTR：如果靠标题党把点击拉上去，完播和点赞会掉， 最终人均时长反而下降。北极星选时长，就是为了堵住这个漏洞。

这张图告诉我们：曝光量前 50% 的内容拿走 69.95% 的曝光，后 50% 只拿 30.05%（数量占比的一半）； 头部 1% 拿到 3.15%，是均匀分布的 3.15 倍。这个集中度比真实短视频平台温和，但足以说明： 只做热门排序，长尾内容永远没有机会；召回层的覆盖率指标必须单独考核。

这张图告诉我们：5000 条视频里 15-30s（1,782 条）和 30-60s（1,734 条）合计占 70.3%， 3 分钟以上只有 86 条（1.7%）。内容池以短视频为主，因此时长特征有一个很强的先验； 反过来，长视频样本极少，模型对"长视频 + 某类用户"的估计会不稳，这也是后面要做分桶统计的原因。

探查阶段最重要的一条结论：这份数据里最有效的信号是"用户 × 品类/质量/时效"的匹配， 而不是"哪个品类整体 CTR 高"。这直接决定了后面的特征设计：要做交叉特征和行为序列， 而不是把 12 个品类 one-hot 丢进 LR 就完事。LR 的 0.8473 已经证明了这一点，DIN 只是把这层匹配做得更细。

PROBLEM问题定义与评估口径：先把"什么叫对"定下来

推荐项目最容易翻车的地方不是模型，是口径。label 怎么定、样本怎么切、离线看什么， 这三件事错了，后面所有数字都不可信。

1）label 定义

y = 1  if click == 1（曝光且点击）
y = 0  if click == 0（曝光但未点击）
样本单位是"一次曝光"，不是"一次请求"，也不是"一个用户"。未点击的曝光就是负样本。

三个容易错的口径，这里明确写死：

  • 未点击 = 负样本，不是缺失。用户看到了但没点，这是明确的负反馈；把它丢掉会让 CTR 被高估到 30% 以上。
  • 完播、点赞不参与点击模型。它们是点击后的条件事件，只用来评估"消费深度"和后续多目标建模。
  • 不构造"未曝光"负样本。数据里没有未曝光的反事实，硬造会把"没被推荐"当成"不喜欢"， 这是样本选择偏差的经典错误。

2）样本构造：按用户内部时间切 80/20

脚本里的切分只有 4 行，但每一行都有原因：

pos_in_user = events.groupby("user_id").cumcount().values     # 用户内序号
user_cnt    = events.groupby("user_id").transform("size").values
is_test     = pos_in_user >= user_cnt * 0.8                   # 每个用户后 20%
tr, te      = ~is_test, is_test

为什么不能随机切？

同一用户相邻几次曝光的行为高度相关，hist 序列、ctr_7d 统计也都来自全期日志。 随机切会让测试样本的"历史"包含测试期的未来行为，AUC 会明显虚高。 更隐蔽的是：ctr_7d 本身就是用全量日志回算的，随机切分时它把 label 的信息带进了训练集。

为什么不能按全局时间切？

日志按用户顺序生成，全局切最后 20% 会把一批用户整段划到测试集——这些用户在训练集里没有任何历史， 序列特征全空，模型只能靠内容特征猜。这不是"难"，而是线上不会出现的情况： 真实服务时每个用户都有历史（哪怕是空历史的新用户，也要走单独的冷启动策略）。

按用户内部时间切同时满足两点：训练用的是"这个用户的过去"，测试用的是"这个用户的未来"， 和线上"用历史预测下一次曝光"的时序关系一致；每个测试用户都有训练期历史，不会出现"无法服务"的样本。

3）离线指标与线上指标的关系

指标衡量什么本项目取值局限
AUC排序能力：随机取一正一负，正样本排在前的概率0.8473 → 0.8584只保序，不保绝对值；对位置偏差不敏感
LogLoss概率预估质量（含校准）0.2939 → 0.2867受样本不平衡影响，绝对值难跨数据集比较

AUC 涨了，线上一定涨吗？不一定。AUC 衡量的是"全体曝光上的排序"，而线上只展示 Top10； 真正决定收益的是头部排序和曝光分配。另外位置偏差会让离线 AUC 包含"位置"这个线上会变的因素。 所以本项目除了 AUC，还看 Recall@100（召回能不能把目标捞回来）和覆盖率（内容池是否被打开）。

为什么召回和排序要分开？因为候选集规模和模型复杂度必须反向匹配。DIN 对 5000 条内容各算一次 attention， 单次请求要 5000 次前向，P99 直接爆掉；而双塔可以把 item 向量离线算好，线上只算一次用户向量 + ANN 检索。 召回负责"别漏"，排序负责"排准"，两者的优化目标、延迟预算、评估指标都不同，混在一起必然有一头做不好。

召回的考核不是"哪个算法最强"，而是"合起来能不能把用户可能点的内容都捞进候选集"。

2）双塔：特征、训练、向量维度、ANN

特征与结构

训练方式

正样本 = 训练期点击；负样本 = 每条正样本配 6 个均匀采样负例，BCE 二分类，温度系数 4（logit × 4）。 输出向量离线灌进 FAISS，线上只算用户向量，ANN 取 Top100。

class Tower(nn.Module):
    def __init__(self, n_ids, dim=32):
        super().__init__()
        self.emb = nn.ModuleList([nn.Embedding(n, 24) for n in n_ids])
        self.mlp = nn.Sequential(nn.Linear(24 * len(n_ids), 96), nn.ReLU(),
                                 nn.Linear(96, 48), nn.ReLU(), nn.Linear(48, dim))
    def forward(self, x):
        v = torch.cat([e(x[:, i]) for i, e in enumerate(self.emb)], 1)
        return torch.nn.functional.normalize(self.mlp(v), dim=-1)

# 1 正 + 6 均匀负例，BCE；负例均匀采样，逼模型学"匹配"而不是"热度"
ue, ie    = u_tower(U_pair[idx]), i_tower(I_pair[idx])

口径：取测试集里有训练期历史的 3000 个用户，ground truth 是他们在测试期（后 20%）点击过的 item 集合， Recall@100 = Top100 命中数 / 该用户测试期点击数，再对用户取平均。覆盖率 = 所有用户 Top100 的并集 / 5000。

反直觉结果：ItemCF 的 4.12% 低于热门的 9.66%。直觉上"协同过滤"应该比"按热度排"聪明， 但这份数据里人均历史点击序列长度只有 1.16（31.8 万曝光里 4.39 万次点击，切到每条样本的历史均值只有 1.16 条）， 用户-物品共现矩阵极其稀疏：绝大多数 item 只被一两个人点过，共现次数为 0 或 1。 ItemCF 的相似度基本是噪声，Top100 自然打不准。

但它不是没价值：覆盖率 86.92% 说明它把长尾内容挖了出来，只是"挖出来"不等于"挖得准"。 这正是多路召回存在的理由——热门保下限、双塔保准确、ItemCF 保覆盖，三路按配额融合， 而不是用一个离线指标选出"最好的那一路"。

融合策略（线上真实配置）：三路各取 Top100，按来源权重（双塔 1.0 / 热门 0.8 / ItemCF 0.6）与模型分归一化后合并， 同一 item 只保留最高分；再按"双塔 ≥ 50%、热门 ≥ 20%、ItemCF ≥ 10%"做配额兜底，防止某一路把候选集吃干。 融合后的真实 Recall 必须在链路里重放才能测，本文不承诺这个数字。

DIN 的核心就是那句"attention 让历史行为针对当前候选加权"。这里的实现是简化版：query 用候选的品类 embedding， key/value 用历史点击的品类序列，mask 掉 padding：

def forward(self, x, hist):
    embs = [e(x[:, i]) for i, e in enumerate(self.emb)]
    s    = torch.stack(embs, 1)                    # B x F x D
    fm   = 0.5 * (s.sum(1) ** 2 - (s ** 2).sum(1)).sum(1)
    out  = sum(l(x[:, i]).squeeze(1) for i, l in enumerate(self.lin)) + self.bias + fm

    h    = self.item_emb(hist)                     # B x L x D，13 个品类（含 padding）
    mask = (hist > 0).float().unsqueeze(-1)
    q    = s[:, 6]                                 # 候选的品类 embedding 作为 query
    att_in = torch.cat([q.unsqueeze(1).expand(-1, h.size(1), -1), h,
                        q.unsqueeze(1) * h], dim=-1)          # [q, h, q*h]
    a    = torch.softmax(self.att(att_in).squeeze(-1)
                         .masked_fill(mask.squeeze(-1) == 0, -1e9), dim=1)
    ctx  = (h * a.unsqueeze(-1)).sum(1)            # 加权后的兴趣向量
    return out + self.mlp(torch.cat([s.flatten(1), ctx], 1)).squeeze(1)

4）怎么解读这 0.0111：收益到底来自哪里

LR → FM（+0.0028）

FM 自动学二阶交叉，但 LR 已经有人工交叉 x_int_cat，所以只多出 0.0028。 结论：人工交叉特征做得好，FM 的增益就有限。这也是工业界很多场景 LR 仍然能打的原因。

FM → DeepFM（+0.0019）

加了 128→64 的 MLP 学高阶交叉，只涨 0.0019，但参数从 0.24K 涨到 37K。 结论：高阶交叉在这份数据里不是主要矛盾，因为核心信号（兴趣 × 品类、质量、时效）基本是二阶的。

DeepFM → DIN（+0.0064）

把"历史点了什么"按候选内容做 attention 加权，AUC 从 0.8520 到 0.8584。 这是四步里最大的一步，说明序列里的兴趣漂移是真信号；但人均序列只有 1.16 条，attention 能发挥的空间有限。

整体 +0.0111 的意义

从 0.8473 到 0.8584，相对提升 1.3%。如果只看这个数字，很容易得出"深度模型没用"的结论。 正确的说法是：在这份数据上，特征 > 模型深度；模型的增量集中在"序列"这一维， 而不是"更深的 MLP"。

DeepFM 的预估均值 0.1446，比真实 CTR 0.1378 高 4.9%；DIN 更高，0.1527，高 10.8%。 这不是"模型变差了"——AUC 和 LogLoss 都更好——而是校准偏移：高容量模型在正样本稀疏时， 对高分区的概率更自信，整体均值被拉高。排序只吃相对顺序时没影响，但一旦要做 多目标加权（CTR × 时长）、eCPM 出价、阈值截断，未校准的 pCTR 会直接把系统带偏。

处理方式：在验证集上做 isotonic regression（保序回归），或对 logit 做 Platt scaling（a·logit+b）。 本项目的校准曲线呈现明显 S 型，isotonic 比单一系数缩放更合适。

5）校准曲线：预估概率 vs 真实点击率

这张图告诉我们：按预估概率分 10 桶后，真实 CTR 与预估并不在对角线上： 低分区（0.004 / 0.0112）被低估，高分区（0.2109 / 0.3505 / 0.631）被系统性高估（真实值为 0.1745 / 0.3057 / 0.5943）。 曲线是 S 型而不是整体平移，所以不能简单乘一个系数；要用保序回归在验证集上重新映射。

为什么排序阶段可以暂时不校准，上线又必须校准？重排用的是 pCTR 的相对大小（MMR 里也是加权排序）， 单调变换不改变顺序；但广告计费、多目标融合、频控阈值都依赖绝对值。 本项目在离线评估里保留未校准值是为了暴露问题，不是认为它没问题。

    # 三路召回并行，任何一路超过 25ms 直接取消，不影响主链路

    return final[:10]

模拟假设，必须说清楚（否则就是编数据）：

① 曝光总量固定为 63,573 条，只改变排序，不模拟"内容更好→用户使用更久→请求变多"的反馈回路。
② 位置偏差沿用观测到的 position_ctr（15.28% / 14.14% / 13.26% / 12.59%），并假设实验组的位置与 pCTR 单调一致。
③ 次日留存字段在数据里不存在。31.2% 是我设定的仿真基线，+1.3pp 是假设值，只能用来演示"怎么讲"，不能当结论。
④ 未做显著性检验。真实 A/B 至少要跑 7 天，用双样本 t 检验或 bootstrap 给置信区间；这里的数字不是抽样估计，没有置信区间可言。
⑤ 没有季节、活动、竞品、客户端改版等外部变量。

为什么 CTR 能涨 8.4%？拆开看是三件事叠加：召回把候选覆盖率从 2% 拉到 11.54%，让"可能被点但热门榜里没有"的内容进入候选； 排序 AUC 提升让候选内部的顺序更合理；重排会主动牺牲一部分 CTR 换多样性，所以最终净增益小于"纯按 pCTR 排"。 这个拆解是方向性的，具体贡献比例需要在线做分流实验才能定。

3）失败与迭代记录

ITERATION 01 随机切分，指标虚高

第一版直接 train_test_split，AUC 好看得不正常。排查发现：同一用户相邻曝光高度相关， 而且 ctr_7d、hist 都来自全期日志，测试集的"未来"漏进了训练集。 改成用户内部时间切分后，LR 落到 0.8473——这才是可信口径。教训：切分方式决定指标上限，先定口径再调模型。

ITERATION 02 DIN 用 item_id 序列，embedding 欠训练

最初把 hist 里的 item_id 直接喂进 DIN 的 attention。5000 个 item 分摊到 4.39 万次点击， 长尾 item 只有个位数样本，embedding 基本是随机初始化，AUC 没有超过 DeepFM 的 0.8520，序列分支等于白加。 换成 13 维品类序列（12 品类 + padding）后，每个品类有上千条样本，AUC 才到 0.8584。 教训：序列建模的前提是序列 token 有足够样本，粒度要按数据量选。

ITERATION 03 双塔用 in-batch softmax，Recall 只有 3.8%

一开始照搬"batch 内其他样本当负例"的做法，但一份 batch 只有 2048 个正样本， 在小数据上负例太少且分布偏，模型学不出区分度，Recall@100 只有 3.8%。 改成 1 正 + 6 均匀负采样 + BCE 后升到 11.29%。 教训：in-batch softmax 依赖大 batch 和大数据，冷启动阶段老老实实做负采样更稳。

ITERATION 04 位置特征直接进模型，离线涨、线上不可用

把 ctx_pos 当普通特征，离线 AUC 涨了一点，但线上排序会改变位置分布， 模型学到的"第 1 位更容易点"在推理时自相矛盾。改成：训练时保留 position 作为偏置项， 预估时固定为基准位（第 1 位），把位置效应从"内容分"里剥离出来；更严格的做法是加一个 position bias 塔做 debias。

ITERATION 05 DeepFM 预估整体偏高，校准没做

DeepFM 的 pCTR 均值 0.1446，真实 CTR 0.1378，高 4.9%；DIN 高 10.8%。AUC 和 LogLoss 都更好， 但绝对值不能直接用于多目标加权。处理：在验证集上拟合 isotonic regression，上线前必须过校准检查。

复盘一句话：这个项目里真正有效的三件事是——把切分口径做对、把品类序列的粒度选对、把多路召回的互补性讲清楚。 无效的三件事是——把 MLP 加深、把 epoch 加多、把 item_id embedding 加大。前者是判断，后者是堆料。

INTERVIEW面试拷问：8 个最容易被追问的点

答案不是背的，是上面每一节压缩成 30 秒能讲完的版本。建议先自己答一遍，再展开看。

为什么召回和排序要分开？直接用 DIN 对全库打分不行吗？

三个原因：算力、目标、可维护性。算力上，5000 条内容每条都跑一次 DIN 前向，单请求就是 5000 次， 而召回层用双塔可以离线把 item 向量算好，线上只算一次用户向量 + ANN 检索，P99 25ms 内完成； 精排只对 100 条候选做，P99 30ms。目标上，召回优化"别漏"（Recall@100、覆盖率），排序优化"排准"（AUC、校准）， 两者指标不同，混在一起会互相拖累。可维护性上，召回可以多路并行、单路降级，排序挂了还能用粗排分兜底。

如果强行全库精排，延迟会直接超出 120ms 预算，而且没必要——召回已经能把命中率做到 11.29%（双塔）， 剩下的是排序问题。

双塔为什么不能做特征交叉？它的表达上限在哪？

因为双塔必须解耦：item 向量要离线预计算并建 ANN 索引，才能在线快速检索。一旦用户塔和内容塔之间做交叉 （比如把 user_id 和 item_id 拼起来过 MLP），item 向量就依赖具体用户，无法预计算，双塔就退化成了精排， 失去"离线建索引"的全部优势。

代价是：用户和内容只能在最后一层做内积，交叉是隐式的。比如"25 岁男性喜欢汽车"这个三元关系， 双塔只能靠两侧 embedding 的内积近似表达，表达力不如 DIN 里的显式交叉。所以工业界的标准做法是 双塔负责召回（宽而快），精排负责交叉（窄而准）。本项目的实测也印证了这一点： 双塔 Recall@100 11.29%，但 AUC 无法和 DIN 比。

负样本怎么选？为什么不用全部未点击曝光？

要分场景。精排的点击模型用曝光未点击做负样本，因为这最接近线上分布：模型要回答的是"这一屏里用户会点哪个"。 本项目 317,866 条曝光、43,933 次点击，负样本 273,933 条，正负比约 1:6.2，直接用全部未点击曝光。

召回的双塔不能用全部曝光——那会让训练被"热门但用户没兴趣"的样本淹没，而且样本量太大。所以用 1 正 + 6 均匀负采样 + BCE。均匀采样会高估"冷门内容"的概率，严格做法要加 propensity 校正 （把采样概率除回去）。

绝对不能用"未曝光"当负样本：没被推荐不等于不喜欢，那是缺失数据，不是负反馈。用了就会把 样本选择偏差固化成模型偏见，热门内容越推越准、长尾永远出不来。

离线 AUC 涨了，线上 CTR 不涨，你怎么排查？

按这个顺序查，从便宜到贵：

① 口径：切分有没有穿越？ctr_7d、hist 是不是用了全期数据？ 正负样本定义有没有变？这是最常见的，本项目第一版就栽在这。
② 评估目标错位：AUC 看全体曝光，线上只看 Top10。要单独算 Top10 的指标，或者用 NDCG@10。
③ 位置偏差：离线样本里的位置分布和线上一不一样？训练用了 ctx_pos，线上位置变了，预估就偏。
④ 特征一致性：线上特征是不是缺失/延迟/口径不同？看特征缺失率和分布漂移。
⑤ 召回瓶颈：排序再好，候选集里没有用户想点的内容也白搭。看召回覆盖率和各路占比。
⑥ 重排/规则抵消：打散、疲劳度、低质过滤可能把模型选出的内容干掉了。
⑦ 实验本身：分流是否干净、样本量够不够、有没有新奇效应。

冷启动怎么办？新用户和新内容分别怎么处理？

新用户：数据里新用户 CTR 14.68%，反而高于老用户 13.82%，说明"点得动"不是问题，"点完不满意"才是。 所以策略不是多给曝光，而是快速试探：热门兜底保证下限 + 品类多样性保证探索 + 用注册侧信息（年龄、城市） 做粗粒度先验 + 前几次曝光按 ε-greedy 主动探索兴趣。本项目受限于数据，只做到"热门 + 兴趣先验"。

新内容：双塔的内容塔只使用内容侧特征（品类、时长、作者、新鲜度、质量分）， 所以新 item 一入库就能算出向量、进入 ANN 索引——这是双塔相对 ItemCF 的关键优势（ItemCF 需要交互才能算相似度）。 再配合重排里 1 个探索坑位（约 10% 流量）和作者历史 CTR 做冷启动加权。

位置偏差怎么处理？你们的做法有什么局限？

数据里首位 CTR 15.28%、末位 12.59%，差 21.4%，这就是位置偏差。三种处理： ① 训练保留、预估固定基准位（本项目做法）：把 position 当偏置特征，推理时统一置为第 1 位， 保证不同候选在同一基准下比较；② IPS 加权：用 1/propensity 给样本加权，需要记录曝光策略的倾向分； ③ position bias 塔：把 p(click) 拆成 p(examined|pos) × p(click|examined)，分别建模。

局限：① 只能消除"固定位置效应"，消不掉"位置 × 内容"的交互（好内容放第 4 位也可能被点）； ② 本项目没有 propensity 日志，做不了严格的 IPS；③ 离线评估仍然是在有偏日志上算的， 所以 AUC 只能做模型间的相对比较，不能当线上绝对水平。

DIN 的 attention 到底有什么用？和 DeepFM 的本质区别是什么？

DeepFM 对历史行为是固定聚合（sum / concat / mean），不管当前候选是什么，用户表示都一样。 DIN 用当前候选做 query，对历史行为加权：候选是"美食"，历史里的"美食"点击权重就高， "汽车"权重就低。本质是让用户表示随候选变化，而不是一人一个固定向量。

本项目的实现是简化版：att_in = [q, h, q*h] 过一个小 MLP 出分数，softmax 时 mask 掉 padding， 加权求和得到兴趣向量，再和 14 个 field 的 embedding 拼起来进 MLP。

效果：DeepFM 0.8520 → DIN 0.8584，+0.0064。增益不大，因为人均序列只有 1.16 条， attention 没有多少历史可加权。如果序列长度到 20+，这个增益会明显放大——这也是为什么工业界要 做长期行为序列。

这个项目最大的不足是什么？

最大的不足是"单目标与北极星不一致"。我优化的是点击率，但业务目标是人均有效播放时长。 CTR 高的内容不一定看得久，数据里也能看到：点击后只有 57.3% 完播。正确做法是多任务 （CTR + 完播 + 时长回归）加权融合，而不是单目标 CTR 排序。

第二是数据是仿真的：没有真实的反事实、没有线上曝光策略变化、没有噪声和异常， 所以离线指标只能证明"方法有效"，不能证明"线上能涨"。第三是 A/B 是模拟的，没有显著性检验。 第四是召回融合没有做端到端重放，融合后的真实 Recall 没有测。

我把这些写在页面上而不是藏起来，是因为面试官一定会问"你觉得哪里不够"—— 能准确说出边界，比多报 2 个点更可信。

三分钟讲法（STAR）：背景是热门榜导致新用户留不住、老用户消费浅、长尾没曝光； 任务是把首页升级成个性化，目标 CTR +8%、时长 +5%；行动是仿真 31.8 万条日志 → 三路召回（双塔 Recall@100 11.29%） → LR/FM/DeepFM/DIN 四代排序（AUC 0.8473 → 0.8584）→ MMR 重排 → 120ms 延迟预算与降级方案； 结果离线指标可复现，模拟 A/B 显示 CTR +8.4%、时长 +5.6%，并明确标注这是模拟、留存数字是假设。 最后补一句最大的不足：单目标 CTR 与北极星时长不一致，下一步做多任务融合。
