02 · BACKGROUND业务背景：政策很多，企业不知道自己能报什么

这是一个典型的"信息不对称"问题，不是一个"排序不准"的问题。企业不是不想申报，是根本不知道有这条政策、也不知道自己够不够条件。 结果就是政策兑现率低：文件发了、预算留着，企业却没拿到——政府和企业两头都亏。

仿真城市设为天津：16 个区县、20 个重点行业、8000 家注册企业。政策分散在发改、工信、科技、人社、税务、金融、商务、生态环境、农业农村、文旅等 10 余个部门， 共 120 条，分属 6 类（资金补贴、税收优惠、融资支持、人才政策、资质认定、场景开放）。每条政策的资格条件由五个维度组合而成：行业 ∩ 地区 ∩ 规模 ∩ 成立年限 ∩ 资质。

🗂️

政策分散在 10+ 部门

同一件事（比如"技术改造补贴"）在不同部门有不同申报入口和口径。企业没有专职政策研究员，小微企业更没有。

🧾

申报条件复杂且刚性

行业、区县、规模、成立年限、资质，任何一项不满足都过不了形式审查。人工比对 8000 × 120 的组合完全不可行。

⏰

窗口短，错过等一年

120 条政策里，1 月截止 17 条、11 月截止 18 条，集中在年初年末。错过申报期，企业损失的是真金白银。

最能说明问题的是这组对照：微型企业平均有 9.05 条政策可申报，但"只看热门政策"的 Top10 召回率只有 7.65%。 也就是说，把全站最热的 10 条政策推给所有人，能命中的可申报政策不到 8%。热门 ≠ 适合，这是政策找人要解决的第一个问题。

一句话记住差别：互联网推荐优化的是"点了没"；政务推荐优化的是"该不该看、能不能报、谁负责"。 前者的错误可以被下一次曝光修正，后者的错误会变成一封投诉信或者一次审计问题。

故意弄脏的三个字段：脚本按 3% 缺失行业、5% 缺失成立年限、2% 缺失规模生成上报数据。去重后共有 755 家企业（9.44%）至少缺一项—— 这就是规则引擎必须面对的"政务数据不干净"。缺失不是异常，是常态：企业注册信息在市场监管、社保、税务之间口径不一致，字段空着比填错更常见。

数据探查

先看分布，再决定用什么方法。行业长尾明显（电子信息 755 家 vs 航空航天 183 家），政策类型完全均衡（6 类各 20 条）， 企业规模以微型为主（3,636 家，45.5%）。这些分布直接决定了后面两件事：热门政策一定偏向普惠型大行业；微型企业才是覆盖重点。

企业可申报政策数集中在 10–14 条（3,183 家），均值 12.66 条，没有任何一家是 0 条。这个分布带来一个结构性结论： Top10 最多只能覆盖 10 / 12.66 ≈ 79.0% 的可申报政策。所以召回率 78.65% 不是"还差 20 个点"，而是已经贴着天花板跑了。

截止月份分布：1 月 17 条、11 月 18 条、12 月 14 条，申报窗口集中在年初与年末。这解释了为什么排序要把"时效"作为特征——同样的匹配度，30 天后截止的政策应该排在 300 天后截止的前面。

04 · RULE ENGINE可申报判定：先保证"不漏"，再谈"准"

政务场景的召回不是"猜你喜欢"，而是"你有没有资格"。这一步必须是确定性的、可审计的、能逐条复现的——所以用规则，不用模型。

eligible(e, p) = 行业(e) ∈ 行业范围(p) ∧ 区县(e) ∈ 地区范围(p) ∧ rank(规模(e)) ≥ rank(最低规模(p)) ∧ 成立年限(e) ≥ 最低成立年限(p) ∧ (资质要求(p) = "不限" ∨ 资质(e) = 资质要求(p)) 五个条件全部为真才可申报。任一条件为假即淘汰，不做"加权打分"——资格不能靠分数打折。

规则伪代码（含缺失字段兜底）

def eligible(ent, pol):
    # 三个可能缺失的字段：缺失即放行，但打上人工核验标记
    if ent.industry is not None and ent.industry not in pol.industries:
        return False, None
    if ent.district not in pol.districts:
        return False, None
    if ent.scale is not None and rank(ent.scale) < rank(pol.min_scale):
        return False, None
    if ent.years is not None and ent.years < pol.min_years:
        return False, None
    if pol.need_qual != "不限" and ent.qual != pol.need_qual:
        return False, None

    # 通过之后，决定这条推荐要不要人工看一眼
    manual = (ent.industry is None) or (ent.scale is None) or (ent.years is None)
    return True, manual

为什么缺失字段是"放行"而不是"过滤"？因为两类错误的代价完全不对称。

漏推：一家确实符合条件的企业，因为行业字段空着被系统静默排除。它不会收到任何提示，也不会知道自己错过了什么——损失是一条可能几十万的补贴，而政府侧的"政策兑现率"也会掉。这种错误没有任何人会发现。

误推：一家不确定是否符合的企业收到一条推荐，点进去发现不满足条件，或者工作人员在核验队列里多花 30 秒确认。损失可观测、可纠正、可解释。

所以策略是：宁可多推，不可漏推。缺失 → 放行 → 标记人工核验。代价是精确率从 100% 降到 91.72%，这个代价是主动选择的，不是模型能力不足。

05 · RETRIEVAL召回层：规则过滤 + 语义排序，而不是二选一

规则能回答"能不能报"，但回答不了"先看哪条"。当一家企业平均有 12.66 条可申报政策、而首页只有 10 个位置时，必须再有一层排序信号。

先把两个名词说人话：

TF-IDF：把一段文字变成"词 + 权重"的向量，再算两段文字的相似度。它只看措辞像不像，不懂"资格符不符合"。 比如企业简介里写了"人工智能"，它就会把《人工智能人才政策》排得很靠前，哪怕这家企业成立才 2 年、根本不满足"满 5 年"。

"召回"在这里有两个意思，别混：①召回层（retrieval）= 从 120 条政策里先捞出一批候选，是一段链路； ②召回率（recall）= 该被推的有没有被推全，是一个评估指标（本文写作 Recall@10）。 前者是"怎么做"，后者是"做得全不全"。

怎么读这四个数

① 热门政策是"最容易做、最没用"的基线。Recall 7.65%、Coverage 8.33%，意味着 120 条政策里只有 10 条被推，其余 110 条永远没有曝光。但它有一个好处：稳定、无风险、解释成本为零。所以它是必须有的一条兜底线，不能当主策略。

② 关键词规则匹配把召回拉到 67.81%，但长尾覆盖不足。它本质上是在用"行业/地区/规模/资质"做加权匹配，比热门强很多，可它只能命中标题和字段里出现过的词。 120 条政策里有 32 条（26.7%）从未进入任何企业的 Top10——这就是"长尾政策覆盖不足"的具体数字，也是我后来加语义召回的直接原因。

③ 纯语义召回的 Coverage 是 100%，Precision 只有 32.15%。它把 120 条政策都覆盖到了，但 Top10 里约 68% 的推荐企业根本不具备资格。 原因很直白：TF-IDF 相似度衡量的是"文本像不像"，不是"条件符不符合"。一家做人工智能的企业，与"人工智能人才政策"文本高度相似， 但政策要求"成立满 5 年"、"最低规模小型"，它可能一条都不满足。语义相关 ≠ 具备资格，这是政务场景最容易犯的错。

④ 规则 + 语义：先保证资格，再排相关性。规则把候选压到"确定能报"的集合，语义在集合内挑出最相关的 10 条。 相比关键词匹配，Recall 从 0.6781 提到 0.7865，Precision 从 0.7864 提到 0.9224，Coverage 从 73.33% 提到 97.5%。 Precision 之所以高于规则引擎的 91.72%，是因为 Top10 只取排序最靠前的头部，头部正好更多来自字段完整的企业——这是"排序把不确定性挤到了长尾"。

78.65% 已经接近天花板。企业平均可申报 12.66 条，首页只放 10 条，理论上限 = 10 / 12.66 ≈ 79.0%。 78.65% / 79.0% ≈ 99.6%，也就是说在"只给 10 个位置"的约束下，这套方案几乎没有可再挖的空间。 想继续提升，只能改产品：扩大展示位、按政策类型分 tab、或者做"未展示的 N 条"入口——那是产品问题，不是算法问题。

为什么政务不能只用向量召回 / 大模型

向量召回解决不了"资格"

Embedding 学的是语义共现，不是布尔条件。它会把"人工智能企业"和"人工智能人才政策"排得很近，但无法保证"成立年限 ≥ 5 年"。 在电商里这只是排序失误，在政务里这是让企业白跑一趟、甚至做出错误承诺。

大模型的三道硬门槛

① 不可审计：审计要的是"哪条规则命中了"，不是一段自然语言理由；② 幻觉：编造截止日期或支持金额，直接造成政府公信力损失； ③ 不可回归：政策改一个字，你需要确定性的回归测试，而不是"重新问一遍模型"。

大模型不是不能用，而是用错位置。在这个项目里它可以做两件事：把政策正文摘要成 3 句话、把命中条件改写成企业听得懂的口语。 这两件事即使出错，也有"原文引用 + 规则命中条件"兜底；而资格判定必须留在规则引擎里。

06 · RANKING排序层：相关性、时效、支持力度，以及一个不能用的特征

召回解决"有没有"，排序解决"先看哪条"。排序分是手写加权，不是训练出来的——因为在这个仿真里，训练只会带来过拟合的假象。

score(e, p) = 1.00 · sim(e, p) // TF-IDF 语义相关性 + 0.35 · 1[行业命中] // 结构化信号，补语义的不足 + 0.25 · 1[地区命中] + 0.0004 · days_to_deadline // 截止越近，权重越高 + 0.0004 · amount_wan // 支持力度 加权系数为手写启发式；仅在规则放行的候选集合内排序，不会把不合格政策排上来。

四个部分的业务含义：语义相关性决定"这条政策是不是在讲我关心的事"；行业/地区命中是显式的结构化确认，避免语义把"全市各行业"的普惠政策顶到最前； 时效用 2026-12-31 − 申报截止 计算，越早截止分越高，因为错过窗口的代价是不可逆的；支持力度让同等条件下金额更高的政策优先，这符合企业的最优决策顺序。

一个绝对不能进模型的特征：企业真实需求强度。生成脚本里有一个隐藏字段 _需求强度，它由"有融资需求、首次申报、研发投入、随机项"合成，决定了企业符合条件后是否真的会申报。 它是效果评估的标签来源，线上永远观测不到。如果把它当特征喂进排序，NDCG 会漂亮得不像话，但上线就崩——这就是典型的标签泄漏。

同理，有融资需求 和 首次申报 也没有进入排序。它们看起来像"用户画像"，但在真实系统里往往来自企业自己填表， 用它排序等于"谁填了融资需求就给谁多推政策"，会形成自我实现的偏差。

NDCG@5 对比

相关性分级采用三档：0 = 不满足硬条件；1 = 满足硬条件；2 = 满足且需求强（用于构造理想排序）。

  • 随机推荐 NDCG@5 = 0.1052：基线，说明这个任务不是"随便排排就能拿高分"
  • 热门政策 = 0.1073：几乎和随机一样，进一步证明"热门 ≠ 适合"
  • 规则 + 语义（无业务分）= 0.9814：资格正确性已经解决，剩下的是顺序问题
  • 规则 + 语义 + 时效/金额（最终）= 0.9933：+0.0119，来自把"快截止的、金额大的"往前放

必须诚实说明：0.9933 是仿真特有的，不代表真实业务水平。在真实场景里，"相关性"由企业的真实需求决定，而需求不可观测、噪声极大、还会随时间变化。 真实政策推荐系统的 NDCG@5 通常在 0.6~0.8 区间。这里能做到 0.99，是因为相关性可以由规则完全观测（满足/不满足硬条件）， 相当于考试时答案就写在题目里。把这个数字原样写进简历，面试官一追问就会露馅。

正确的说法是："在相关性可完全观测的仿真环境下达到 0.9933，验证了排序逻辑的正确性；真实业务需要人工标注或申报反馈才能评估，预期在 0.6~0.8。"

政务推荐的解释不是"模型觉得你可能会喜欢"，而是"你满足这 5 条，政策原文这么写，截止这天，最高给这么多，从这里办理"。这是一张可核对的清单，不是一段话术。

"可解释"在政务里的三个作用

🤝

企业信任

企业不信任"系统推荐"，但会信任"我符合这 5 条、原文这么写、截止这天"。可核对的信息比高分的模型更能促成申报行为。

🔍

工作人员复核

窗口人员不该重新跑一遍资格判断。命中条件 + 原文引用让他能在 30 秒内确认或驳回，人工核验队列才有可能被真正消化。

🧾

审计留痕

推荐日志要能回答：当时用的是哪一版政策、哪一版规则、命中了哪几条、为什么没推另外 110 条。这是审计要的材料，不是模型要的指标。

08 · FAIRNESS & COMPLIANCE公平性与合规：不是"平均分配"，而是"别把人漏掉"

政务推荐最容易被误解的一点：不同规模企业的"Top10 覆盖率"天然不同，这不是歧视，而是"固定展示位 + 不同可申报池大小"的算术结果。

先解释那个容易误读的现象。大企业平均可申报 20.28 条，但 Top10 只能覆盖 50.54%；微型企业只有 9.05 条可申报，Top10 却能覆盖 96.82%。 这不是"给大企业推得少"，恰恰相反——大企业的可申报池更大，10 个位置被稀释得更厉害。这是曝光公平（每家都有 10 个位置） 与 满足率公平（可申报池被覆盖的比例） 之间的差别。

该看哪个口径？看"至少收到 1 条推荐的企业占比"——四组都是 100%，没有任何一家企业被系统完全忽略。 再看曝光条数的分布：基尼系数 0.0436，接近完全均等（0 表示每家曝光条数完全相同，1 表示全部集中在一家）。 这说明系统没有把流量倾斜给大企业或某个区县。

如果反过来，微型企业的覆盖率只有 40%、而大型企业 95%，那才是问题——那意味着系统在"帮强者更强"。

但也要承认这套评估的局限。基尼系数只能说明"曝光量"均衡，不能说明"曝光质量"均衡。政策之间的金额、兑现难度差异很大， 如果大企业拿到的都是 500 万的融资贴息、微型企业拿到的都是 5 万的场景开放，曝光均等并不等于机会均等。真实项目里还需要按"金额加权曝光"再算一遍。

合规清单（6 条，任何一条缺失都不该上线）

  • 最小必要：只取判定所需的 12 个字段；不接入纳税明细、社保明细、银行流水，不因为"可能有用于模型"就多要数据。
  • 脱敏：报表与日志中的企业名称脱敏（津达科技有限公司 → 津达**有限公司）；对外只展示统一社会信用代码后 4 位。
  • 授权：企业登录后只能看到自己的匹配结果；工作人员按"辖区 + 事项"授权，越权查询留痕并可追溯。
  • 留痕：每次推荐记录政策版本、规则版本、命中条件、排序分、时间戳；支持"这条为什么推给我"的事后回溯。
  • 人工兜底：字段缺失的企业（755 家）与高金额政策（如 ≥ 100 万）强制人工核验后再触达，不直接群发。
  • 不自动化决策：系统只做推荐与提示，资格认定与资金审批由业务部门完成；不做自动通过，也不做自动拒绝。

一个容易忽略的合规点：排序特征的选择本身就是合规决策。这个项目里，规模、营收、专利数、资质只作为硬条件参与"能不能报"， 不作为排序特征参与"先推谁"。如果把它们放进排序分，系统就会系统性地把大企业、高营收企业排在前面—— 虽然每家都有 10 个位置，但位置顺序会影响点击与申报，这就构成了隐性歧视。

迭代记录：三次踩坑，三次修正

ITERATION 01 只用关键词规则 → 长尾政策覆盖不足

Coverage 只有 73.33%，120 条政策里有 32 条从未进入任何企业的 Top10。原因：标题和字段里没出现"人工智能"这类词的政策，永远匹配不上。 修正：加入 TF-IDF 语义召回，Coverage 提到 97.5%。

ITERATION 02 纯语义召回 → 误推率过高

Coverage 到 100%，但 Precision 只有 32.15%：Top10 里近七成企业根本不具备资格。企业点进去发现"我不符合"，信任度反而下降。 修正：把规则放在语义前面，语义只在"确定可申报"的候选集合内排序，Precision 提到 92.24%。

ITERATION 03 缺失字段直接过滤 → 系统性漏推

为了追求精确率，最初把"行业为空 / 年限为空 / 规模为空"的企业直接排除。结果是 755 家企业（9.44%）被静默漏掉， 而且漏掉的恰恰是数据填报能力最弱的小微企业——这是最不该发生的错误。 修正：改为"放行 + 人工核验"，Recall 回到 100%，Precision 降到 91.72%，用一个 755 家的核验队列换取零漏推。

10 · DEPLOY落地与集成：离线批处理 + 在线查询的混合架构

政策不是实时变化的，企业也不是每秒都在登录。所以这套系统的正确形态是"每天全量算一次，登录时补算增量"，而不是一个追求 QPS 的在线推荐服务。

离线保证全量与可回溯，在线保证新政策不延迟。两条路径必须共用同一份规则配置，否则会出现"批处理和实时算出来的结果不一样"。

为什么是"批处理为主、在线为辅"

离线（T+1 全量）：每天 02:00 对 8,000 × 120 = 96 万个候选对做规则判定与排序，产出推荐结果表。优点是可全量重算、可回溯、可回归测试；政策与规则版本都固化在结果里，审计时能精确还原"当时为什么推这条"。

在线（登录时补算）：企业登录时，只需补算近 24 小时新增或变更的政策——通常是个位数——再与离线结果合并。语义模型（TF-IDF 矩阵）随包加载进内存，单次计算在毫秒级，不需要 GPU，也不需要向量数据库。

一致性保障：离线与在线共用同一份规则配置文件（行业/地区/规模/年限/资质五元组）和同一个模型文件；每次发布带版本号，结果表记录版本号，出现差异可以按版本回放定位。

这个项目的边界：哪些话不能说

可以说的：规则可申报判定 + 语义召回的混合架构、用 8,000 家企业 / 120 条政策复现了漏推与误推的完整权衡、 缺失字段"放行 + 人工核验"的策略选择、每条指标都有脚本可复现。

不能说的："上线后申报率提升 X%"——页面里的 A/B 是明确标注的假设，没有真实流量； "用了大模型语义匹配"——这里是 TF-IDF，连向量检索都没用； "零漏推"——Recall 1.0 是相对仿真标签而言，真实场景中政策原文的模糊条款无法被规则完整表达； "公平性已解决"——基尼系数 0.0436 只说明本次推荐结果的分布相对均衡，不代表现实中的申报结果公平。

为什么主动划边界：面试官最容易追问的就是边界。你先说清楚哪些没做、为什么没做， 比等他问出来再解释，可信度完全不同。

11 · INTERVIEW面试拷问：8 个一定会被追问的问题

这个项目的价值不在于指标多高，而在于每个取舍都能说清"为什么"。下面 8 个问题，基本覆盖了面试官对政务 / 行业项目的全部疑问。

为什么不用大模型直接做政策匹配？

因为资格判定是布尔问题，不是生成问题。大模型输出的是概率性文本，而"能不能申报"必须给出确定性结论，并且要能回答审计的追问："哪条规则命中了？政策原文哪一句？"

具体有三个不可接受的风险：① 幻觉——编造截止日期、支持金额、申报条件，企业据此准备材料，损失是真实的；② 不可审计——一段自然语言理由无法作为审计证据，也无法做回归测试；③ 不可控——政策改一个字，你需要的是确定性的 diff 和回归，而不是"再问一遍模型看它怎么说"。

大模型可以用在正确的位置：政策正文摘要、命中条件的口语化改写、客服问答。这些位置即使出错，也有"原文引用 + 规则命中条件"兜底；资格判定必须留在规则引擎。

漏推和误推怎么权衡？为什么精确率只有 91.72% 也能接受？

先看代价是否对称。漏推：一家符合条件的企业被静默排除，它不会知道自己错过了什么，损失可能几十万，而且没有任何人会发现这个错误。误推：企业收到一条不确定的推荐，点开发现不符合，或者工作人员在核验队列里多花 30 秒——可观测、可纠正、可解释。

所以策略是"缺失字段放行 + 标记人工核验"，代价是 Precision 从 100% 降到 91.72%（误推 9,148 条，8.28%），换回 Recall = 100%（FN = 0）。这个 91.72% 不是模型能力上限，是主动选择的业务取舍。

但如果误推率继续上升到 15%~20%，我会分级处理：低金额政策继续放行，高金额（如 ≥ 100 万）政策改为"先人工预审再触达"。权衡点不是固定值，它取决于人工核验队列的承载能力和政策金额的量级。

没有标注数据，你怎么评估效果？

仿真环境里"真值"由生成器持有（行业、地区、规模、年限、资质五个条件的逻辑与），所以 P/R、NDCG、公平性都能精确计算——这是仿真的优势，也是它的局限，必须主动说明。

真实场景我会用三个替代信号：① 部门审核结果与退回原因做弱标注，计算"推荐→申报→通过"的转化与退回归因；② 人工抽检 500~1000 条推荐，算 Precision 的置信区间，这是最可靠的手段；③ 在线指标（查看率、咨询率、申报率、投诉率）做趋势监控。

最难的是"应报未报"——真实场景里你观测不到企业本来能报但没报的政策，所以 Recall 无法直接计算。工程上只能做"政策全量回放 + 业务专家复核"抽样估算漏推率，并把缺失字段企业单独拉出来盯。

怎么证明你的系统没有歧视特定规模或地区的企业？

先定义口径，再拿数据说话。我用三个指标分组统计（按规模、按区县）：① 覆盖率——每组"至少收到一条推荐"的企业占比，四组都是 100%，没有企业被完全忽略；② 人均曝光条数——基尼系数 0.0436，接近完全均等；③ 可申报覆盖比例——用于解释差异来源。

然后做反事实检查：同一家企业，只改规模字段，排序分不变——因为规模、营收、专利、资质只作为硬条件，不作为排序特征。这一点很关键：如果把它们放进排序分，即使每家都有 10 个位置，位置顺序也会系统性偏向大企业，形成隐性歧视。

最后要承认局限：曝光量均等 ≠ 机会均等。政策的金额和兑现难度差异很大，真实项目还应该做"金额加权曝光"的公平性分析，并按区县看政策供给是否本身就不均衡。

规则和模型怎么分工？为什么不是端到端模型？

规则管"能不能"，模型管"先看哪条"。规则给出确定性的可申报集合（五维硬条件），模型只在集合内排序（语义相关性 + 行业/地区命中 + 时效 + 支持力度）。

这么分工有三个好处：① 任何一条推荐都能回答"为什么给你"——因为资格来自规则，逐条可核对；② 规则可以配置化，政策条件变化不需要重新训练；③ 模型出错最多是"顺序不理想"，不会变成"推荐了不能申报的政策"，错误被限制在可控范围内。

端到端模型在这个场景里不划算：样本量小（8,000 家企业、120 条政策）、真值可由规则完全确定、可解释性是硬需求。用深度模型去拟合一个已知的布尔函数，除了增加不可解释性，没有收益。

政策更新了怎么办？新增、修改、下架分别怎么处理？

政策表带 policy_id + 版本号 + 生效/截止时间，三类变更分开处理：

新增：进入次日 02:00 的全量批处理；同时在线查询路径会补算近 24 小时新增政策，企业当天登录就能看到，不必等到第二天。

修改：生成新版本，旧版本保留。规则字段（行业/地区/规模/年限/资质）走配置化，不写死在代码里；修改后跑一遍回归集，确认影响范围（哪些企业新增/失去了资格）。

下架：结果表打 invalid 标记而不是物理删除，前端不再展示但日志保留；已触达的企业要能被追溯——审计问"为什么当时推了这条"，你要能拿出当时的政策版本。

企业信息缺失怎么办？能不能用模型补全？

三层处理：① 放行 + 标记人工核验——缺行业/规模/年限时不做淘汰，只标记，755 家企业（9.44%）进入核验队列；② 文案降级——触达文案从"您符合条件"改为"您可能符合，请补充信息后确认"，避免做出错误承诺；③ 引导补全——在一网通办入口提示企业补字段，补全后次日重算。

不能用模型猜。用行业分布或企业名称去推断"它大概是制造业"，一旦猜错，系统就会给出一个看似确定的错误结论。政务场景里，"我不确定，请人工确认"是可接受的；"我猜你是制造业"是不可接受的。

这个项目最大的风险是什么？

不是模型效果，是"解释错了"和"数据过期"。

解释错了：政策原文引用的是旧版本，或者支持金额、截止日期展示错误——企业按错误信息准备材料，损失直接且不可逆。措施是原文引用带版本号、展示前校验有效期、高金额政策强制人工复核。

数据过期：企业已经变更行业或区县，系统还在按旧画像推荐。措施是每日增量同步 + 全量对账，关键字段变更有变更日志，推荐结果表记录画像快照时间。

第三个风险是信任崩塌：一旦企业连续收到几条"我不符合"的推荐，它就不再点开任何推荐，后面做得再好也没用。所以误推率要盯得比召回率更紧，尤其是在项目早期。

如果只记一句话带走：这个项目证明的不是"我会调模型"，而是"我知道在政务场景里，确定性、可解释、可审计比多两个点的 AUC 更重要， 并且我能用规则、语义、排序三层结构把这三件事同时做到"。这也是它和互联网推荐项目放在一起时，最有差异化的地方。
