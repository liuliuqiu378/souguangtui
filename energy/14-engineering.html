SPECIAL B5 · ALGORITHM ENGINEERING

算法工程实践：让结果可复现、可测试、可回滚

第 6 章讲了服务化的骨架。这一章补“工程素养”：代码怎么组织、测试怎么写、版本怎么管、CI 怎么跑、线上怎么观测、成本怎么估。这些不炫技，但决定了别人敢不敢把你的模型放进生产。

预计 90 分钟 前置：第 6 章 产出：一套可交付的工程规范 性质：实践 / 落地
四个词定义“工程化”

可复现：同一份代码 + 同一份数据 + 同一个种子，任何人能跑出同样的结果。可测试：改一行代码，能在几分钟内知道有没有弄坏东西。可观测：线上出问题，能回答“哪里、什么时候、为什么”。可回滚：新版本不行，能在一分钟内退回上一版。缺任何一个，都还停在“Demo”。

项目结构：让陌生人也能找到东西

推荐目录结构
project/
├── README.md               # 怎么跑、数据从哪来、指标口径
├── pyproject.toml          # 依赖与版本锁定
├── configs/
│   ├── base.yaml           # 特征名单、超参、路径
│   └── prod.yaml           # 环境差异，不写密钥
├── src/
│   ├── data/               # 读取、清洗、校验
│   ├── features/           # 训练与服务共用
│   ├── models/             # 训练、预测、评估
│   └── service/            # API、调度、监控埋点
├── scripts/                # 一次性入口：train.py、backfill.py
├── tests/                  # 单元、集成、黄金样本
├── artifacts/              # 模型、指标、特征重要性
└── data/                   # 不提交仓库；用 DVC/对象存储
一条硬规则：特征代码只有一份

训练与服务必须 import 同一个 features/build.py，不能各写一份。项目一和项目二都遵守这点：训练脚本和 api.py 调用同一套特征函数。这是避免“离线 1.78%、线上 6%”最有效的手段。

配置与密钥：不要把密码写进代码

内容放哪注意
特征名单、超参YAML / Python 常量进版本库，可 review
环境差异环境变量 / 配置中心不要用 if-else 写死路径
数据库密码、Token密钥管理 / 环境变量绝不进 Git；日志里要脱敏
模型文件对象存储 + 版本号不进 Git；用 DVC/MLflow 管
数据快照数据湖 / 对象存储按日期分区，可回放

日志：为“事后破案”而写

日志不是 print。好的日志要能回答：谁在什么时候、用什么输入、得到了什么输出、耗时多少、是否降级。

结构化日志 + 请求上下文
import logging, json, time, uuid

log = logging.getLogger("forecast")

def handle(req):
    rid = str(uuid.uuid4())[:8]
    t0 = time.perf_counter()
    try:
        y = predict(req)
        log.info(json.dumps({
            "rid": rid, "event": "ok",
            "origin": str(req.origin_ts), "n_points": len(y),
            "latency_ms": round((time.perf_counter()-t0)*1000, 1),
        }, ensure_ascii=False))
        return y
    except Exception as e:
        log.exception(json.dumps({"rid": rid, "event": "error", "msg": str(e)}))
        raise
坑：日志里打印完整负荷序列

一次请求带 169 个点，日志会被撑爆，还可能包含敏感数据。正确做法：记录摘要（点数、均值、缺失率、首末值）和 rid，需要时再用 rid 去对象存储取原始请求。

测试：从“我试过”到“有证据”

层级测什么例子
单元测试函数级逻辑特征函数输出列名、缺失处理、边界值
数据测试数据质量与分布无重复、缺失率阈值、容量范围、时间连续
集成测试端到端链路请求 → 特征 → 模型 → 响应格式
黄金样本输出与基准一致同一输入，预测结果与基准误差 < 1e-6
回归测试指标不退化新模型在固定测试集上 MAPE 不高于上一版 + 0.1
tests/test_features.py
import pandas as pd, numpy as np
from src.features.build import make_features

def test_lag_uses_previous_day():
    idx = pd.date_range("2024-01-01", periods=200, freq="h")
    s = pd.Series(np.arange(200, dtype=float), index=idx)
    f = make_features(s)
    assert f.loc[idx[30], "lag24"] == s.loc[idx[6]]

def test_no_future_leak():
    # 构造一个“未来突变”的序列，验证特征不受影响
    idx = pd.date_range("2024-01-01", periods=100, freq="h")
    s = pd.Series(1.0, index=idx)
    f1 = make_features(s)
    s2 = s.copy(); s2.iloc[80:] = 999
    f2 = make_features(s2)
    assert (f1.iloc[:80].fillna(-1) == f2.iloc[:80].fillna(-1)).all().all()

第二个测试很关键：它把“不泄漏未来”从口头承诺变成了可执行断言。以后任何人改特征，只要破坏了这条规则，CI 会立刻拦住。

版本管理：代码、数据、模型分开管

对象工具要点
代码Git小步提交、分支、PR review；commit 写“为什么”
数据DVC / 数据湖按日期分区，记录快照 ID
模型MLflow / 对象存储模型 + 特征列表 + 超参 + 指标 + 训练数据范围
环境Docker 镜像镜像 tag 与模型版本绑定
实验MLflow / 表格每个实验记录参数、指标、数据版本
模型版本里必须有什么

模型文件、特征顺序、预处理参数、阈值、训练数据时间范围、代码 commit、评估指标、负责人。少一样，出问题时就无法回答“这个版本是怎么来的”。第 6 章的 artifacts/ 规范就是为此设计的。

CI/CD：把检查自动化

每次提交自动跑：格式检查 → 单元测试 → 数据测试 → 训练冒烟 → 镜像构建。任何一步失败就阻止合并。

.github/workflows/ci.yml（骨架）
name: ci
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.10"}
      - run: pip install -r requirements.txt
      - run: ruff check src tests
      - run: pytest -q
      - run: python scripts/smoke_train.py   # 小样本训练 + 断言指标
CI 里不要跑全量训练

全量训练可能几十分钟，拖慢反馈。正确做法是“小样本冒烟”：取最近 7 天数据、50 棵树，只验证链路能跑通、指标不崩。全量训练放到独立的定时任务或发布流水线里。

部署形态：批、在线、流

形态场景技术重点
批处理每天 0 点出 96 点预测Airflow + 容器任务幂等、可重跑、补数
在线 API平台点开即查、实时调度FastAPI + Docker延迟、限流、降级
流式秒级告警、实时特征Kafka + Flink水位线、乱序、状态管理
Dockerfile（最小可用）
FROM python:3.10-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY src ./src
COPY artifacts ./artifacts
EXPOSE 8000
CMD ["uvicorn", "src.service.api:app", "--host", "0.0.0.0", "--port", "8000"]
K8s 只需要知道四件事

Deployment 管副本与滚动更新；Service 提供稳定入口；HPA 按 CPU/自定义指标扩缩容；ConfigMap/Secret 管配置与密钥。算法工程师不一定要会运维集群，但要知道自己的服务是怎么被调度、怎么被限制资源的。

性能：先量，再优化

手段做法适用
向量化用 pandas/numpy 代替 for 循环特征计算
批量推理一次 predict 多个测点树模型吞吐远高于逐条调用
缓存缓存历史负荷、节假日表、特征重复请求、批量任务
并发线程/进程池、异步 IOIO 密集（查库、调外部）
降级超时返回上次结果或简单基线在线服务保可用

项目一的单次 24 点预测在普通笔记本上是毫秒级，真正的瓶颈通常在“取历史数据”和“网络”。所以先测端到端延迟，再看模型推理耗时，不要盲目优化模型。

监控：四层指标，缺一不可

层次看什么告警示例
可用性请求成功率、错误码、健康检查5 分钟错误率 > 1%
性能P50/P95/P99 延迟、吞吐P95 > 500 ms 持续 5 分钟
数据质量缺失率、越界率、延迟到达某测点缺失率 > 5%
模型效果精度、漂移、告警量、命中率MAPE 周环比上升 > 0.5 个点
告警要分级，否则没人看

P0：服务不可用、结果明显错误 → 立即电话；P1：精度显著下降、数据大面积缺失 → 工作时间内处理；P2：单测点异常、轻微漂移 → 日报汇总。所有 P0/P1 都要有 runbook（先查什么、怎么回滚），否则半夜被叫起来只会慌。

成本与容量：别让方案跑不起

成本项怎么估优化方向
算力训练时长 × 单价；推理 QPS × 单次耗时小模型、批处理、按需扩容
存储原始数据 + 特征 + 模型 × 保留周期分区、压缩、冷热分层
数据库写入量、查询量、保留天数降采样归档、只存必要标签
人力维护、值班、迭代自动化监控与重训练

一个常见误区：为了“技术先进”上实时流处理，结果数据量根本不需要秒级，成本翻倍、故障点变多。先问“业务能等多长时间”，再决定架构。

安全与合规：能源数据不是普通数据

数据安全

用户用电数据可推断作息、生产情况，属于敏感信息。要做脱敏、最小权限、访问审计；导出数据要审批。

模型可解释

告警要能解释“为什么报这个测点”，否则现场不认。特征重要性、同业对比、原始曲线是最低要求。

合规边界

窃电认定、费用追缴是执法/商务行为，算法只能提供线索，不能替代现场核查与法律程序。写报告时要区分“模型判定”和“事实认定”，这既是专业，也是保护自己。

协作与交付：让结果被采用

需求评审：先定验收标准

“预测准”不是标准。“日前 24 点，MAPE ≤ 2.5%，峰段 ≤ 2%，接口 P95 < 200 ms”才是。验收标准要在动手前写下来。

中期对齐：给可看的中间结果

不要憋大招。第二周就给出数据质量报告和基线，让业务尽早纠偏。

上线评审：风险清单

数据依赖、降级方案、回滚步骤、责任人、监控项，逐条确认。

复盘：把事故变成资产

每次 P0/P1 都写清时间线、根因、影响、改进项。三个月后，这些就是面试里最好的故事。

常见坑

坑后果正确做法
密钥写进代码/Notebook泄露、审计不过环境变量 / 密钥管理
只测“能跑”，不测边界线上空输入直接崩单元测试覆盖空值、越界、缺列
模型文件不带特征列表列顺序错，结果离谱模型包存 features + 冒烟测试
日志打印全量数据存储爆炸、隐私风险摘要 + rid
没有回滚方案事故恢复以小时计镜像 tag + 一键回滚
CI 跑全量训练反馈慢，没人等小样本冒烟
监控只看服务，不看效果模型悄悄失效三个月加精度/漂移/告警量指标

常见问题

Q1：小团队也要搞这么全吗？
不必全上，但四件事不能省：配置与密钥分离、特征代码一份、模型包带特征列表、能回滚。其余按团队规模逐步补。工程化的目的是降低协作成本，不是堆工具。
Q2：没有 K8s，怎么部署？
Docker + 一台服务器 + systemd/supervisor 就能跑；批任务用 cron。等并发、可用性要求上来再考虑 K8s。不要为了简历上写 K8s 而增加故障面。
Q3：模型效果监控没有真实标签怎么办？
用代理指标：输入分布漂移、预测分布变化、与同业/历史基线偏离、人工反馈。真实标签到达后再补算精度。关键是“有信号”，而不是“等完美指标”。
Q4：CI 里怎么测数据质量？
用断言或轻量框架：行数范围、主键唯一、时间连续、缺失率上限、数值范围、枚举值合法。数据测试失败应阻断训练，而不是只发告警——脏数据训出来的模型比没有模型更危险。

自测：你的项目能交付吗

  • 新同事能在 10 分钟内按 README 跑出和你一样的指标。
  • 改坏特征代码，CI 能在 5 分钟内报错。
  • 模型包里能查到特征顺序、训练数据范围、代码 commit。
  • 线上出错时，能用一个 rid 找到那次请求的输入摘要与输出。
  • 新版本出问题，能在 1 分钟内回滚到上一版。
  • 能说清你的方案在 10 倍数据量下大概需要多少算力与存储。
