算法服务化与上线运维

Notebook 里 MAPE 1.78% 不算数。这一章讲：怎么把模型封成别人能调用的接口、怎么保证线上结果和离线一致、怎么发现模型悄悄变差、以及上线后最常见的七种事故。这套工作常被统称为 MLOps（机器学习运维），落到本岗位，就是“让算法稳定地跑在线上”。

预计 90 分钟 前置：第 4、5 章（建议先跑通项目一） 产出：两个可调用的 FastAPI 服务

为什么“会调库”不够，还要会服务化

招聘要求里写得很直白：“将训练完成的预测、异常检测算法封装成标准化微服务，对接后端平台调用；完成算法版本管理、线上效果监控、迭代调优。”这句话翻译成日常工作是：

接口（API）到底是什么：一个点菜窗口

把服务想成餐馆：平台不需要进厨房，只要对着窗口说“要一份未来 24 小时预测”，窗口递出一张单子。这个窗口就是 API。JSON 是单子的格式——带字段名的文本，例如 {"load_mw": 812.4}；POST 是“提交一张新单子”的动作。你写服务，就是开这个窗口，并保证不管谁来、什么时候来，递出来的单子格式都一样。

平台同学不会读你的 Notebook

他们只认 HTTP 接口：给一个 JSON，返回一个 JSON。你要把“读 CSV、造特征、预测”这一串动作，变成一个稳定的 POST。

线上数据和你训练时不一样

时区、单位、缺失、列顺序、节假日表，任何一处不一致，结果就会错，而且不一定报错——这是最危险的。

模型会“过期”

园区新入驻了企业、电价调整、设备改造，都会让分布漂移。没有监控，你会在三个月后才发现模型早就废了。

出问题要能定位

是数据没来、特征错位、模型版本回滚，还是调用方传错？日志和指标必须能回答这些问题。

一个模型服务的完整生命周期

离线训练与评估

产出模型文件 + 特征列表 + 指标报告 + 训练数据时间范围。这四样必须一起归档，缺一不可。

打包与版本号

模型、特征顺序、预处理参数、阈值、依赖版本冻结成一个可追溯的版本，例如 load-lgb-2024.12.1。

服务封装

FastAPI 提供接口，启动时加载模型（只加载一次），请求时只做特征拼装与推理。

联调与灰度

先影子模式（只记录不生效）跑一周，对比线上输出与离线回放是否一致，再切 10% 流量。

监控与告警

看四类指标：可用性、延迟、输入数据质量、预测精度/漂移。任意一类越界都要有人收到通知。

迭代与回滚

新模型上线必须能一键回滚到上一版；回滚时间要写进 SLA。

先定契约（接口约定），再写代码

服务化的第一件事不是写 FastAPI，而是和调用方把输入输出字段定死。契约不清，后面全是扯皮。下面是项目一实际使用的契约。

POST /v1/forecast · 请求
{
  "origin_ts": "2024-12-31T00:00:00",
  "load_history": [
    {"ts": "2024-12-24T00:00:00", "load_mw": 812.4},
    // ... 至少 169 个逐小时点，按时间升序，最后一个是 origin 时刻
  ],
  "weather_forecast": [
    {"ts": "2024-12-31T01:00:00", "temp_c": -2.1}
    // ... 24 个点，未来 1~24 小时
  ],
  "holidays": ["2025-01-01"]
}
POST /v1/forecast · 响应
{
  "model_version": "load-lgb-2024.12.1",
  "origin_ts": "2024-12-31T00:00:00",
  "points": [
    {"ts": "2024-12-31T01:00:00", "horizon": 1, "load_mw": 795.2},
    // ... 共 24 个点
  ],
  "meta": {"n_features": 25, "latency_ms": 11.8}
}
为什么输入要“历史序列 + 预报”，而不是“25 个特征”

如果让调用方直接传 25 个特征，等于把特征工程的责任推给了平台——他们不可能知道 same_hour_yesterday 怎么算。正确分工是：平台传原始数据（负荷历史、气象预报、日历），算法服务内部造特征。这样特征逻辑只在一处维护，模型迭代不影响调用方。

完整代码在 projects/p1_load_forecast/api.py，这里只讲骨架。核心原则：模型在启动时加载一次，请求里只做拼装和推理。

线上第一大事故：特征列顺序变了

LightGBM 按列位置读特征。如果服务里用 df[FEATURES] 之前列被打乱，模型不会报错，只会安静地给出离谱结果。防御手段有三层：① 模型包里存特征名；② 推理前 assert list(X.columns) == FEATURES；③ 服务启动时用一条样例做冒烟测试，输出和离线基准比对，差异超过阈值就拒绝启动。

批量与实时：两种调用模式

模式典型场景实现要点注意
实时单点平台点开某个测点，查看未来 24 小时一次请求一个 origin，返回 24 点延迟目标 < 200 ms；要限流防刷
批量日跑每天 0 点给全园区 40 个测点出预测一个请求带多个测点，或离线任务批量写库失败要能重跑，且幂等
回放/回测验证新模型在历史 3 个月的表现离线脚本，不走服务必须用与线上一致的特征代码

批量场景不要“循环调 40 次接口”。正确做法是一次请求传数组，服务内部一次性构造特征矩阵、一次 predict。树模型批量推理的吞吐远高于逐条调用。

版本管理：模型不是单个文件

一个可回滚的模型版本至少包含下面这些内容。少一样，出问题时就查不清。

artifacts/ 目录规范
artifacts/
├── model.joblib            # {"model": LGBMRegressor, "features": [...]}
├── metrics.json            # 测试区间、各模型指标、分时段误差
├── feature_importance.csv
├── train_manifest.json     # 训练数据时间范围、行数、超参、代码 commit
└── model.card.md           # 用途、输入输出、已知局限、负责人

train_manifest.json 里建议记录：训练起止时间、样本数、特征列表、超参、随机种子、评估指标、代码版本号。面试时能拿出这个文件，可信度立刻不一样——它证明你不是“跑完就丢”。

监控：上线后到底看什么

类别指标越界怎么办
可用性请求成功率、P99 延迟、错误码分布>1% 错误或 P99 > 500 ms 告警；先查依赖与日志
输入质量缺失率、越界值比例、历史长度不足的请求数输入异常直接拒绝（4xx），不要“猜一个值”返回
预测精度T+1 回算 MAPE、按小时/按测点 MAPE、偏差（bias）连续 3 天高于基线 50% 触发复查
分布漂移特征 PSI、预测值分布均值/方差PSI > 0.2 提示显著漂移，评估是否重训
业务效果购电偏差、需量超标次数、告警确认率这是最终指标，按月复盘

漂移检测：PSI 怎么算

PSI（Population Stability Index）衡量“当前分布”和“训练分布”的差异。做法是把训练集某个特征分成 10 个分箱，统计两边的占比，再算：

psi.py · 20 行实现
def psi(base: np.ndarray, cur: np.ndarray, bins: int = 10) -> float:
    edges = np.unique(np.quantile(base, np.linspace(0, 1, bins + 1)))
    b = np.histogram(base, bins=edges)[0] / len(base)
    c = np.histogram(cur,  bins=edges)[0] / len(cur)
    b = np.clip(b, 1e-6, None)
    c = np.clip(c, 1e-6, None)
    return float(np.sum((c - b) * np.log(c / b)))

# 经验判据：<0.1 稳定；0.1~0.2 需关注；>0.2 显著漂移，评估重训
漂移了不一定要立刻重训

先判断是数据漂移还是概念漂移。如果只是特征分布变了但精度没掉（比如负荷整体上移，模型仍跟得上），可以只更新标准化参数或基线；如果精度持续下降，才重训。盲目重训可能把模型带偏，尤其是在标签延迟到达的场景。

精度回算：T+1 才能算 MAPE

预测服务当天只能拿到预测值，真实负荷要等第二天。所以精度监控是延迟一天的：每天凌晨用昨日真实值回算过去 7 天的滚动 MAPE，低于阈值就告警。这一步要写成定时任务，不能靠人手动跑。

依赖版本必须锁死

LightGBM、numpy、pandas 的版本差异可能导致模型加载失败或结果微小偏移。生产镜像里要用 pip freeze 生成精确版本，不要写 lightgbm>=4 这种范围。模型文件与训练环境的版本要一起记录。

七种线上事故与排查顺序

现象最可能原因排查动作
返回全 0 或全相同值特征矩阵列错位、或某列全为 NaN 被填充成常数打印前 3 行特征，与离线回放逐列比对
预测值整体偏高/偏低固定比例单位不一致（kW vs MW）、倍率未还原核对输入单位与训练数据单位
延迟突然从 20 ms 涨到 2 s每次请求重复加载模型、或日志写满磁盘确认模型只在启动时加载；查磁盘与 GC
节假日预测全错节假日表过期，或时区按 UTC 解析检查年节假日配置；统一用本地时区
接口 422 大量增加调用方传了空值、时间格式变化、字段改名看错误详情；契约变更要版本化
精度缓慢下降但无报错分布漂移（新企业入驻、设备改造）跑 PSI + 分测点 MAPE，定位漂移来源
同一请求两次结果不同模型未固定随机性、或特征里有 now()禁用推理期随机性；特征只依赖输入

上线检查清单

  • /health 返回模型版本与特征数，可用于探活。
  • 模型与特征列表一起加载，推理前断言列顺序。
  • 输入长度、时间连续性、单位、时区都有校验，错误返回 4xx 而不是 500。
  • 启动时跑一条冒烟样例，与离线基准结果比对。
  • 每条请求记录：时间、版本、输入摘要、输出摘要、耗时。
  • T+1 精度回算任务已配置，连续 3 天越界会告警。
  • 特征 PSI 日报已配置，阈值 0.2。
  • 上一版模型可直接回滚，回滚步骤写在 runbook 里。
  • 依赖版本已锁定，镜像可重复构建。
  • 接口有超时与限流，避免被单个调用方拖垮。

常见问题

Q1：为什么不直接把模型给平台，让他们自己调？
因为特征工程、预处理、阈值都是算法的一部分。让平台重写一遍，必然出现“训练和推理不一致”。服务化的本质是把算法边界收拢到一个可测试的单元里，平台只负责传原始数据和展示结果。
Q2：小项目也要上 Docker 和监控吗？
演示项目至少要能一条命令启动、有 /health、有日志。Docker 不是必须，但它是“换台机器也能跑”的最省事方式。监控可以先从“每天回算一次 MAPE 写进 CSV”开始，不必一上来就上 Prometheus。
Q3：模型多久重训一次？
没有固定答案，看漂移速度。常见做法：月度定时重训 + 精度触发重训（连续 3 天劣化 50%）+ 事件触发（电价调整、新企业入驻）。重训前必须回测，不能直接覆盖线上模型。
Q4：怎么保证离线指标和线上一致？
三条：① 特征代码只有一份，离线和线上共用；② 定期做“回放测试”，用线上真实请求的输入跑离线模型，逐点比对；③ 上线前用历史某天做端到端复现，误差应在浮点精度级别。
Q5：没有 Kubernetes，怎么部署？
一台 Linux 服务器 + systemd + uvicorn 就能跑。关键是：进程守护、日志轮转、开机自启、版本目录切换。K8s 解决的是多副本与弹性，不是“能不能上线”。面试时说清这个取舍，比堆名词更好。
