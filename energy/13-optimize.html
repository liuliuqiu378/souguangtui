SPECIAL B4 · OPTIMIZATION

优化调度与需求响应：把预测变成可执行的计划

预测回答“会怎样”，优化回答“该怎么做”。这一章从零讲清线性规划怎么建模、储能约束怎么写、需量电费怎么进目标函数，以及一个计划从“算出来”到“执行下去”还差什么。

预计 100 分钟 前置：第 2、3 章；建议先读项目二 产出：能独立写出储能调度模型 性质：实践 / 决策
先分清：预测、规则、优化

预测给出一条未来曲线；规则说“谷段就充、峰段就放”；优化在所有约束下找“总成本最低”的那组动作。规则简单但常常不是最优——比如峰段放电放到一半，需量反而被抬高；优化能同时考虑电价、需量、SOC、效率与并网限制。

优化建模四步：变量、目标、约束、求解

决策变量：你要决定什么

每个时段的充电功率、放电功率、购电量、SOC、是否充放电（0/1）。变量必须是“能下发给设备”的量。

目标函数：你在优化什么

电度电费 + 基本电费（需量）+ 退化成本 + 偏差惩罚。注意单位统一：元、kW、kWh、小时。

约束：什么不能做

SOC 上下限、功率上限、充放电互斥、首末 SOC、并网容量、设备可用性。少一条，结果就可能“数学最优、物理不可行”。

求解与校验

选求解器，检查求解状态（最优/可行/不可行），再做物理校验：SOC 轨迹、功率、电费是否与手算一致。

一个判断模型好坏的标准

把优化结果拿给现场运维看，他能不能在 1 分钟内判断“这能不能执行”？如果他说“电池不可能同时充放”“这个点已经超容”“首末 SOC 对不上”，说明约束没建全；如果他说“这和我平时操作差不多，但更省”，模型就成立了。

储能建模：五个约束缺一不可

储能是最典型的“看起来简单、建起来容易错”的对象。下面五条是底线。

约束数学表达为什么必须有
SOC 递推SOC[t+1] = SOC[t] + η·ch[t]·Δt − dis[t]/η·Δt能量守恒；效率要分别作用在充和放上
SOC 上下限SOC_min ≤ SOC[t] ≤ SOC_max保护电池；项目用 10%~90%
功率上限0 ≤ ch[t], dis[t] ≤ P_maxPCS 与并网容量限制
充放互斥ch[t] ≤ P_max·z[t]，dis[t] ≤ P_max·(1−z[t])物理上不能同时充放；否则模型会“免费搬电”
首末 SOCSOC[0] = SOC[T] = 50%保证可持续，不把电池“用空”换收益
坑：不写互斥，模型会同时充放

如果允许 ch 和 dis 同时为正，模型可以在同一时段“充 100 kW、放 100 kW”，只损失效率，却可能骗过需量约束或制造虚假的 SOC 平衡。规模小时收益看起来不大，但这是典型的“数学最优、设备不可行”。只有在负电价、弃光补贴等特殊价格结构下，纯 LP 才可能真的选择同时充放——项目二没有这些情形，所以用了更简单的 LP。

需量控制：最容易被忽略的“第二笔账”

峰谷套利省的是电度电费，需量控制省的是基本电费。两者可能冲突：为了套利在峰段前多充，可能把峰值抬高，反而多交需量费。

把最大需量写进目标函数
# 引入一个变量 demand，表示计费周期内的最大购电功率
demand = LpVariable("demand", lowBound=0)

# 每个时段的购电功率都不超过 demand
for t in T:
    prob += buy[t] <= demand

# 目标：电度电费 + 需量电费（元/kW·月 或 元/kW·日）
prob += (lpSum(price[t] * buy[t] * dt for t in T)
         + demand_price * demand)

这个写法有一个前提：需量周期与优化窗口一致。如果需量按月统计，而你只优化一天，就需要把“历史月最大需量”作为已知下界代入，否则会低估需量成本。项目二做了简化：按日需量计价（1.2 元/kW·日），因此可以直接在日窗口内建模。

削峰与套利的优先级

多数园区应该先保证不超需量，再谈套利。因为需量费是确定的、按月收；套利收益受价差和效率影响，且可能被需量上升抵消。模型里可以通过给需量项更高的权重来体现这个优先级，而不是靠事后人工调整。

完整模型：储能日前调度（PuLP 写法）

下面用 PuLP 写一遍，结构最直观。项目二实际用的是 scipy.optimize.linprog（HiGHS）的纯 LP 版本：在电价为正、效率小于 1 的条件下，“同时充放”只会额外损失能量，不可能更优，所以可以省掉 0/1 变量。参数与结果都对得上：3000 kWh、1000 kW、单程效率 0.95、SOC 10%~90%、首末 50%。

dispatch.py · 储能日前优化（节选）
import pulp as pl

T = 96                      # 一天 96 个 15 分钟时段
dt = 0.25                   # 小时
CAP, PMAX, ETA = 3000, 1000, 0.95
SOC_MIN, SOC_MAX, SOC0 = 0.1, 0.9, 0.5

prob = pl.LpProblem("storage", pl.LpMinimize)
ch  = [pl.LpVariable(f"ch{t}",  0, PMAX) for t in range(T)]
dis = [pl.LpVariable(f"dis{t}", 0, PMAX) for t in range(T)]
soc = [pl.LpVariable(f"soc{t}", SOC_MIN*CAP, SOC_MAX*CAP) for t in range(T+1)]
z   = [pl.LpVariable(f"z{t}", cat="Binary") for t in range(T)]
buy = [pl.LpVariable(f"buy{t}", lowBound=0) for t in range(T)]
demand = pl.LpVariable("demand", lowBound=0)

prob += soc[0] == SOC0 * CAP
prob += soc[T] == SOC0 * CAP

for t in range(T):
    prob += soc[t+1] == soc[t] + ETA*ch[t]*dt - dis[t]*dt/ETA
    prob += ch[t]  <= PMAX * z[t]
    prob += dis[t] <= PMAX * (1 - z[t])
    prob += buy[t] == load[t] + ch[t] - dis[t] - pv[t]
    prob += buy[t] <= demand
    prob += buy[t] >= 0

prob += (pl.lpSum(price[t] * buy[t] * dt for t in range(T))
         + 1.2 * demand)
prob.solve(pl.HiGHS(msg=False))
坑：目标里的时间单位

price 是元/kWh，buy 是 kW，必须乘 dt=0.25 才是元。忘了乘，收益会放大 4 倍；乘错（比如用 15 分钟却乘 1），收益会缩小。这类错误在报告里最致命，因为数字看起来“很合理”。

需求响应：基线算错，响应白做

需求响应的结算逻辑是“响应量 = 基线 − 实际用电”。所以基线方法直接决定收益。

基线方法做法特点
10 中取 3响应日前 10 个工作日中，取负荷最高的 3 天同时段平均简单、常见；对天气变化不敏感
高 5 中 10前 5 个工作日与前 10 个工作日的均值取较高者更保守，减少“基线虚高”
回归基线用温度、星期、历史负荷拟合更准；需要足够历史与特征
机器学习基线用预测模型给出“不响应时的负荷”最灵活；可解释性和审计要求高
坑：基线被“做低”

如果响应前几天的负荷被人为压低，基线就会偏低，响应量看起来变小甚至为负。反过来，基线方法也可能被利用来“刷补偿”。所以真实项目里基线要可审计、要固定规则、要保留原始数据，不能由算法随意调整——这是合规问题，不只是技术问题。

可调量怎么估

需求响应不是“想少用就能少用”。可调量取决于：哪些负荷可中断（空调、照明、非关键产线）、能停多久、恢复时会不会反弹、用户体验是否可接受。工程上通常分三档：

秒级~分钟级

储能、变频空调、快速切断的非关键负荷。适合调频/爬坡。

15 分钟~1 小时

照明、部分产线、充电桩降功率。最常见的 DR 场景。

小时级以上

检修调整、生产排程、蓄冷蓄热。适合长时间削峰。

光伏、充电桩与 V2G

对象建模要点常见问题
光伏出力上限 = 预测出力；弃光要显式建模把光伏当负负荷，忽略了弃光与限功率
充电桩到达时间、离开时间、电量需求、功率上限只做有序充电，不考虑用户离开约束
V2G车辆可作为储能，但要留足出行电量忽略电池损耗与用户接受度
净负荷购电 = 负荷 − 光伏 + 充电 − 放电符号错，导致“越充越少”
“鸭形曲线”是什么

光伏占比高时，净负荷在午间被压得很低，傍晚光伏退坡、负荷上升，形成陡峭的爬坡，形状像鸭子的背和脖子。它带来两个问题：午间可能弃光或负电价，傍晚爬坡需要快速资源。储能正好填这个缺口，这也是“光储”经常一起出现的原因。

虚拟电厂：把分散资源聚成一个“电厂”

虚拟电厂（VPP）不发电，它聚合可调资源（储能、充电桩、空调、工业负荷），在市场上像一个电厂一样申报和响应，赚取价差、补贴或辅助服务费用。

资源聚合

把多个园区的储能、可中断负荷汇总，形成可调容量曲线。要区分“可上调”和“可下调”。

预测与申报

预测基线负荷与可调量，按市场规则申报。申报过高会被考核，过低则浪费容量。

实时调度

按指令分解到各资源，考虑通信延迟、设备响应时间、用户约束。

计量与结算

按基线核算响应量，处理偏差、考核、补偿。数据要可审计。

VPP 的技术难点不在优化，而在“可信”

聚合资源的可调量是估计出来的，实际响应可能打折；通信中断、设备拒动、用户反悔都会导致偏差。所以 VPP 系统里，可观测性、指令确认、兜底策略比优化算法更关键。面试如果只讲“我用 LP 优化”，会被追问“资源没响应怎么办”。

不确定性：预测错了，计划还能用吗

方法思路代价
确定性用点预测直接优化简单；预测偏差大时计划失效
场景法生成多个负荷/光伏场景，优化期望成本场景数增加，求解变慢
鲁棒优化假设最坏情况在不确定集内保守，可能牺牲收益
机会约束允许小概率越限建模复杂，需要分布假设
CVaR优化尾部风险适合对极端损失敏感的场景
工程上更常用的折中：滚动优化

不做复杂的随机优化，而是每 15 分钟用最新预测重新优化未来 24 小时（滚动时域，MPC 思想）。预测误差被不断修正，计划自然收敛。代价是需要稳定的在线求解与指令下发链路。

从计划到执行：还差最后一公里

计划可执行性校验

检查功率、SOC、并网容量、设备状态；对不可行点做降级（例如限制充放功率）。

指令下发与确认

通过 PCS/EMS 下发功率指令，等待设备确认；超时重试或告警。不能假定“发了就会执行”。

闭环修正

每 15 分钟读取实际功率与 SOC，与计划比对；偏差大就重新优化。

人工干预与兜底

检修、消防、并网限制时，人工接管必须优先；算法要有“退出”开关。

坑：把优化结果当成“必然发生”

报告里写“节省 14.7 万元”，但实际执行率只有 60%，真实收益就大打折扣。项目二的结果是“按计划完全执行”的口径，正文里已明确。真实项目必须同时报计划收益与实际收益，并分析差额来自预测误差、执行偏差还是电价变化。

常见问题

Q1：为什么不直接用规则“谷充峰放”？
规则在简单场景下接近最优，但遇到需量约束、光伏、多段电价、SOC 边界时容易失效。规则无法同时权衡“套利收益”和“需量成本”，也无法处理“今天要不要留电给明天”的问题。优化不是更高级，而是能显式表达权衡。
Q2：MILP 太慢怎么办？
先看规模：96 个时段、1 个储能，MILP 通常秒级。变慢常见于多储能、多场景、细粒度。可以：① 用 LP 松弛再修复；② 减少 0/1 变量（用价格差排除同时充放）；③ 用滚动窗口；④ 换 HiGHS/Gurobi。
Q3：电池衰减怎么进模型？
简化做法是给每 kWh 吞吐加一个退化成本（元/kWh），或限制日循环次数；精细做法是用 SOH 曲线、循环深度与温度建模。项目二没有计退化成本，这是一个已知简化，面试时要主动说明。
Q4：需求响应的收益怎么算才靠谱？
先确定基线方法与补偿单价，再算“响应量 × 单价 − 生产损失 − 恢复反弹成本”。特别注意：如果响应导致之后反弹，净收益可能为负；如果基线本身被下压，响应量会被高估。

自测：能不能独立建模

  • 能写出储能 SOC 递推式，并说明效率放在分子还是分母。
  • 能解释为什么需要充放电互斥，以及 big-M 怎么写。
  • 能写出“最大需量”进入目标函数的两行约束。
  • 能说清项目二为什么电费下降但购电量增加。
  • 能解释需求响应基线为什么会被“做低”，以及怎么防。
  • 能说出滚动优化相比一次性优化的好处与代价。
