时序数据工程进阶：把脏数据变成可信特征

第 3 章讲了“该不该补、该不该删”的判断。这一章往下钻一层：用什么代码做、为什么会做错、做错之后模型会怎么坏。目标是你能独立写出可复现、可上线的特征流水线，而不是在 Notebook 里拼拼凑凑。

预计 100 分钟 前置：第 2、3 章 产出：一条可复用的特征流水线 性质：技术基础 / 实践
先明确：什么叫“可信特征”

三个条件同时满足才算：① 每个值在预测发生的那一刻真的拿得到；② 时间对齐正确，shift(24) 就是 24 小时前，不因缺失而错位；③ 训练和服务用的是同一套代码、同一套口径。缺一条，离线分数再漂亮，上线也会崩。

时间列：最容易错、也最不该错

时序项目里 80% 的“玄学 bug”都和时间有关。先把四个概念分清：

概念含义出错后的表现
时区同一时刻在不同地区的本地时间不同，中国为 UTC+8整体错 8 小时，日曲线形态“看着对但时间全偏”
时间戳语义这个 timestamp 是区间起点、终点，还是瞬时值15 分钟数据整体前移/后移一格，峰值对不上
采样约定一天 96 点还是 96 段；00:00 属于哪一天日电量少算/多算一格，月度累计对不上账
夏令时部分国家每年调表，出现 23/25 小时的一天如果数据源跨时区或多国项目，会出现重复/缺失小时
坑：把本地时间当 UTC 存

“2024-08-01 00:00”如果不带时区，不同系统会各自解释。做法：存储统一用 UTC 或带时区的时间戳，展示时再转本地。项目里用 pd.Timestamp(..., tz="Asia/Shanghai") 或统一存 +08:00，并在数据字典里写清楚。

时间处理的正确顺序
# 1) 解析时明确时区；没有时区就显式指定
ts = pd.to_datetime(df["ts"], utc=True).dt.tz_convert("Asia/Shanghai")

# 2) 先建完整索引，再对齐数据（顺序不能反）
idx = pd.date_range(start, end, freq="15min", tz="Asia/Shanghai")
s = df.set_index("ts")["power_kw"].reindex(idx)

# 3) 检查是否有重复时间戳（重复会让 reindex 直接报错）
dup = df.duplicated(["meter_id", "ts"]).sum()

# 4) 检查采样间隔是否都是 15 分钟
gaps = s.index.to_series().diff().value_counts().head()

96 点、日历与“业务时间”

15 分钟粒度一天 96 点，这是电力结算和需量统计的常见口径。但“一天”在业务上不等于自然日：工厂的班次可能从 08:00 开始，商业体的营业日可能从 10:00 算起。做特征时必须区分自然时间和业务时间。

日历特征怎么造为什么有效
小时 / 15 分钟槽ts.hour、ts.hour*4 + ts.minute//15捕捉日内形态与班次
星期 / 是否周末ts.dayofweek、is_weekend工作日与周末曲线不同
节假日 / 调休维护一张节假日表，标注“放假/调休上班”中国调休会让“周六”变成工作日，只靠星期几会错
节前节后天数距离最近节假日的天数（有符号）春节前后负荷渐变，不是突变
月份 / 季节ts.month，或正弦编码空调负荷有明显季节性与温度阈值
正弦/余弦编码sin(2πh/24)、cos(2πh/24)让 23 点和 0 点在数值上接近，树模型也能受益
业务日序号按班次/营业日重定义 day_id跨零点的夜班不应被切成两天
构建日历表（含调休）
cal = pd.DataFrame({"ds": pd.date_range(start, end, freq="D")})
cal["dow"] = cal["ds"].dt.dayofweek
cal["is_weekend"] = (cal["dow"] >= 5).astype(int)

# 用一张“工作日表”覆盖周末判断：调休上班的周六 is_workday=1
workday = pd.read_csv("calendar_cn.csv", parse_dates=["ds"])
cal = cal.merge(workday[["ds", "is_workday", "is_holiday"]], on="ds", how="left")
cal["is_workday"] = cal["is_workday"].fillna((cal["dow"] < 5).astype(int))
一个容易被忽略的细节

节假日表不是“放假日列表”，而是“每一天是不是工作日”的完整映射。只标放假、不标调休，会把调休上班的周六当成周末，导致那天的预测整体偏低。项目一的 is_holiday 和 is_workday 是分开的两个字段，就是为了避免这个问题。

pandas 时间工具箱：12 个必会操作

操作用途注意
resample("1h").mean()降采样，功率取均值默认跳过 NaN，要同时看 count()
resample("1D").sum()电量按日汇总单位是 kWh 还是 kW×0.25，先统一
asfreq("15min")只改索引频率，不聚合会插入 NaN，不会填充
reindex(full_idx)补齐缺失时段必须先建完整索引，否则 shift 错位
ffill(limit=8)短缺口前向填充limit 单位是“行数”，不是小时
interpolate(limit=8)线性插值长缺口不要插，会造出虚假平台
rolling(96, min_periods=72)滑窗统计窗口是否包含当前点要明确
shift(96)昨日同期依赖索引完整，否则是“上一条记录”
groupby("meter_id").shift(1)按测点分组滞后不分组会把别的测点数据串进来
merge_asof按时间就近对齐（如气象、工单）必须排序，direction 要选对
tz_localize / tz_convert指定 / 转换时区本地化前必须是 naive 时间
to_period("M")按月聚合、月度对齐跨年边界要检查
按测点分组造滞后，避免串行
# 错：所有测点混在一起 shift，M002 会拿到 M001 的值
# df["lag96"] = df["power_kw"].shift(96)

# 对：先按测点分组，再在组内排序、shift
df = df.sort_values(["meter_id", "ts"])
df["lag96"] = df.groupby("meter_id")["power_kw"].shift(96)
df["roll96_mean"] = (df.groupby("meter_id")["power_kw"]
                        .transform(lambda x: x.shift(1).rolling(96, min_periods=72).mean()))

聚合规则：功率取均值，电量取求和

这是最基础、也最常错的一条。15 分钟功率 → 1 小时：功率取平均；电量取求和。如果数据单位是 kW 而你想得到 kWh，还要乘 0.25。

原始量目标正确聚合典型错误
功率 kW（15min）功率 kW（1h）mean()用 sum()，数值放大 4 倍
功率 kW（15min）电量 kWh（1h）sum() × 0.25直接 sum() 当 kWh
电量 kWh（15min）电量 kWh（1h）sum()用 mean()，少算 3/4
功率 kW（15min）最大需量 kWmax()，再按月取最大按日取平均当需量
累计电度 kWh区间电量diff()，处理倒走直接当功率建模
坑：累计电度换表/清零导致 diff 出现负值

换表后读数从 0 开始，diff() 会出现一个大负数。处理方式：先把负值置空，再用容量上限做合理性填充，并记录“换表事件”。不要简单取绝对值，那会造出一个虚假的巨量尖峰。

缺失：先判断机制，再选方法

缺失不是“补上就行”。不同机制要用不同策略，否则会系统性扭曲分布。

机制含义能源场景例子处理
完全随机（MCAR）缺失与任何变量无关偶发通信丢包短缺口插值，长缺口置空 + 标记
随机（MAR）缺失与其他可观测变量有关高温天空调满负荷时网关过载丢数用相关变量建模填补，或加缺失标记
非随机（MNAR）缺失与缺失值本身有关窃电者故意断表、故障时设备直接掉线不能简单插值；缺失本身就是强特征
缺失处理的标准流程
# 1) 统计连续缺失长度，而不是只看缺失率
na = s.isna()
grp = (na != na.shift()).cumsum()
runs = s[na].groupby(grp[na]).size()      # 每一段连续缺失的长度

# 2) 短缺口：按时间线性插值（最多 2 小时 = 8 个 15min 点）
s_filled = s.interpolate(method="time", limit=8, limit_area="inside")

# 3) 长缺口：保持 NaN，并加标记列，让模型知道“这里不可信”
s_missing_flag = s.isna().astype(int)

# 4) 记录：缺失率、最长缺口、影响时段，写进质量报表
report = {"missing_rate": s.isna().mean(),
          "max_gap": int(runs.max()) if len(runs) else 0}
缺失标记为什么有用

如果某测点夜间经常断线，模型看到“缺失标记=1”就知道这条读数不可靠，可以更多依赖同业基线。反过来，如果所有缺失都被悄悄插值填平，模型会把“插出来的假数据”当真，异常检测会漏报——因为窃电导致的断表被“补”成了正常值。

异常值：先问“它是错误还是事实”

异常值不一定要删。设备故障、窃电、极端天气都是真实发生的，它们恰恰是业务关心的信号。你要区分的是数据错误和真实极端事件。

方法怎么算适合 / 不适合
3σ偏离均值 3 倍标准差适合近似正态；负荷曲线非正态，容易误杀峰谷
IQR超出 Q1−1.5IQR 或 Q3+1.5IQR稳健，适合整体分布筛查
MAD用中位数绝对偏差代替标准差对极端值稳健，适合单测点
滚动中位数偏离局部中位数超过阈值适合捕捉“卡死”“突跳”，但要设最小窗口
STL 残差分解后对残差做阈值能扣掉日周期，适合负荷曲线
业务规则负值、超容量、倒走、连续恒定最可靠，应优先于统计方法
稳健异常标记（MAD + 业务规则）
med = s.rolling(96, min_periods=48).median()
mad = (s - med).abs().rolling(96, min_periods=48).median()
robust_z = 0.6745 * (s - med) / mad.replace(0, np.nan)

flag = (robust_z.abs() > 3.5)
flag |= (s < 0) | (s > capacity * 1.2)     # 业务规则优先
# 注意：只标记，不直接删；让模型/规则决定是否忽略

特征工程进阶：从“能用”到“有区分度”

第 4 章的五类特征是基础版。真实项目里，决定效果的往往是下面这些“更贴近业务”的特征。

特征族怎么造适用场景
多阶滞后lag 1/4/24/96/672（按粒度换算）短期预测；滞后阶数覆盖日、周周期
滑窗统计mean/std/min/max/分位数，窗口 4/24/96/672描述近期水平与波动
同比/环比今日同时刻 / 昨日同时刻 − 1抵消量级差异，适合多测点
傅里叶项sin/cos(2πkt/24)、周周期项线性模型、神经网络；树模型可选
事件距离距最近节假日/大修/停产的天数渐变型影响，比 0/1 标记更细
跨测点特征同类型测点均值、园区总负荷占比异常检测、缺失时的替代信号
天气派生体感温度、制冷/制热度日、辐照累计空调负荷、光伏
业务标记班次、检修、限产、节假日值班工业负荷，往往是最强特征
目标编码按测点/类型的历史均值编码多测点全局模型；必须用时间切分内统计
跨测点特征与傅里叶项
# 同类型测点的同时刻均值：既能做特征，也能做异常基线
df["peer_mean"] = (df.groupby(["meter_type", "ts"])["power_kw"]
                     .transform("mean"))
df["peer_ratio"] = df["power_kw"] / df["peer_mean"].replace(0, np.nan)

# 日周期与周周期的傅里叶项
hour_frac = df["ts"].dt.hour + df["ts"].dt.minute / 60
df["sin_d"] = np.sin(2 * np.pi * hour_frac / 24)
df["cos_d"] = np.cos(2 * np.pi * hour_frac / 24)
df["sin_w"] = np.sin(2 * np.pi * df["ts"].dt.dayofweek / 7)
坑：目标编码用了全量数据

用全量历史算“测点平均负荷”再喂给模型，等于把测试期的信息带进训练。正确做法：只用训练窗口内的数据统计，且按时间滚动计算；或者干脆用“同类型同时刻均值”这种不依赖标签的替代。

从 CSV 到数据管道：规模上来之后怎么办

项目里 23 万行，pandas 足够。真实园区可能是几百个测点、几年数据，甚至上亿行。这时要换工具，但思路不变：分区、增量、可重跑。

工具解决什么什么时候该用
Parquet列式压缩存储，按日期/测点分区数据超过内存、需要反复扫描列
DuckDB单机 SQL 分析，直接查 Parquet几千万行以内，替代“pandas + 数据库”
Spark分布式批处理上亿行、跨天批量特征、离线训练
Flink流处理、窗口聚合实时特征、秒级告警、在线监控
Kafka消息队列，解耦采集与计算多源数据、削峰、实时管道
Airflow / DolphinScheduler任务编排、依赖、重试、补数每天固定跑的特征/训练/报表任务
时序数据库按时间写入与范围查询在线服务取历史负荷、监控
一个务实的演进路径

① 先用 pandas + Parquet 把逻辑跑对；② 数据变大后换 DuckDB，SQL 不改太多；③ 再大或需要多人协作，才上 Spark/Flink；④ 调度从 cron 升级到 Airflow。不要一上来就搭大数据平台——大多数园区项目根本用不到，反而拖慢迭代。

分区与增量：不要每天全量重算

按日期分区的目录约定
data/
├── raw/meter=2024-08-01.parquet
├── clean/meter=2024-08-01.parquet
└── features/
    ├── dt=2024-08-01/part-0.parquet
    └── dt=2024-08-02/part-0.parquet

# 增量：只重算受影响的分区（含回补窗口）
# 滞后特征需要“回看”，所以重算范围 = 目标日期 - 最大滞后窗口

分区设计要围绕“重跑成本”来做。如果最大滞后是 7 天，那么修改某天的数据，至少要重算它之后 7 天的特征。这个“回补窗口”必须写进调度配置，否则会出现特征与原始数据不一致。

训练与服务一致性：最隐蔽的线上事故

离线 MAPE 1.78%，上线变成 6%，最常见的原因不是模型过时，而是线上算特征的方式和训练时不一样。

典型不一致

时区不同、聚合顺序不同、缺失填充不同、滞后窗口含不含当前点不同、单位不同（kW vs W）、节假日表版本不同。

怎么防

特征代码只写一份，离线和在线共用；上线前用同一批原始数据回放，逐特征比对；把特征版本号写进模型包。

特征回放比对（黄金样本）
# 离线：用历史原始数据算一遍特征
offline = build_features(raw_snapshot)

# 在线：调服务内部的同一函数（或导出的同一模块）
online = service_build_features(raw_snapshot)

diff = (offline - online).abs()
assert diff.max().max() < 1e-6, diff.stack().sort_values().tail()
Point-in-time 正确性

凡是“按测点/类型统计历史均值”的特征，都必须保证统计窗口的截止时间不晚于预测起点。这叫 point-in-time join。做法：给每条统计记录带上 valid_from / valid_to，关联时按时间匹配，而不是直接 merge。项目规模小时容易忽略，一旦上线就会变成“看起来用了历史，其实用了未来”。

坑后果正确做法

常见问题

Q1：缺失率 1% 也要处理吗？
要看缺失的位置。如果集中在某几个测点的连续时段，1% 也足以毁掉滞后特征；如果随机散布且都是单点，影响很小。先看“最长连续缺口”和“受影响测点占比”，再看总缺失率。
Q2：插值会不会造假数据？
会，所以只对短缺口插值，并保留缺失标记。插值的目的是让时间轴连续、滞后特征不错位，不是假装数据完整。长缺口应该让模型知道“这里没有观测”。
Q3：一定要用时序数据库吗？
不一定。数据量小、只做离线训练时，Parquet + pandas 更简单。时序数据库的价值在“高频写入 + 按时间范围查询 + 在线服务”。选型要看访问模式，不要为了简历堆技术。
Q4：特征几十个、几百个，怎么筛？
先按业务逻辑删掉“预测时拿不到”的，再看重要性/相关性/方差，最后用时间切分的验证集做前向选择。不要用全量相关性筛选，那会泄漏；也不要把“重要性低”直接等同于“没用”，树模型会分摊相关特征的重要性。
